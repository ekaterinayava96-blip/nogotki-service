## ИИ-интеграция: GigaChat (Сбер)

- Провайдер: **GigaChat API** (AI_PROVIDER=gigachat)
- Модель: **GigaChat-2-Pro**
- Авторизация: Authorization Key из проекта GigaChat API → access token (действует 30 мин) → Bearer

## Backend (Node.js): переход на встроенный SQLite

**Когда:** работа с новым бэкендом сервиса записи (`backend/`, пакет `nogotki-backend`).

**Что сделано.**
- Подключение к базе переведено с внешней библиотеки `better-sqlite3` на **встроенный модуль Node.js `node:sqlite`** (`DatabaseSync`) — внешнее native-зависимое расширение больше не требуется (`connection.js`).
- `better-sqlite3` удалён из `dependencies` (`package.json`), слежение за внешними ключами, WAL, `busy_timeout`, `synchronous` перенесены на `PRAGMA ...` через `db.exec`.
- Резервное копирование (`backup.js`) переведено с `db.backup()` на `VACUUM INTO` (в node:sqlite метода `backup` нет).
- Миграции (`runMigrations.js`), сид (`seed.js`) и сброс (`reset.js`) используют только `db.exec / prepare / transaction / close` — совместимы с node:sqlite.

**Требование к версии Node (зафиксировано в `package.json`, поле `engines`):**

```
"engines": { "node": ">=22.13" }
```

Почему **22.13**: модуль `node:sqlite` появился в Node 22.5.0 как экспериментальный (требовался флаг `--experimental-sqlite`); с версии **22.13.0** флаг больше не нужен — модуль доступен из коробки. Версии ниже 22.13 не дадут модуль без флага именно в этом виде.

**Дополнительная защита:** в `backend/.npmrc` включён `engine-strict=true`, поэтому на сервере `npm install` завершится ошибкой, если перенести проект на неподходящую версию Node (ниже 22.13).

**Какую версию ставить на сервер:**

- **Минимум:** Node.js **22.13.0** и выше (строка 22.x, предпочтительно последний патч).
- **Рекомендуется:** актуальная **LTS-строка 22** (или новее, если вышла новая LTS), например `22.x` последней ветки.
- Проверка на сервере перед деплоем: `node --version` (должно быть `v22.13.0+`).
- Установка на Linux-сервере через nvm: `curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash`, затем `nvm install 22 && nvm use 22`.
- После установки: `npm ci` (или `npm install`), запуск `npm run start:check` — проверка конфигурации и миграций перед приёмом запросов.

## Backend (Node.js): схема БД, миграции и тестовые данные

**Когда:** разработка бэкенда сервиса записи (`backend/`, пакет `nogotki-backend`), этап «база данных».

**Что сделано.**
- Схема спроектирована по `docs/db-schema.md`: **11 таблиц** (services, masters, studio_info, master_services, master_schedule, work_blocks, studio_closures, bookings, clients, users, payments) + **8 индексов**. Ключевые решения: свободные слоты вычисляются на лету (отдельной таблицы слотов нет), цены в копейках, время — локальный ISO-текст `YYYY-MM-DD HH:MM:SS`, роль `client` добавлена в `users` (миграция `002`).
- Миграции: `backend/src/db/migrations/001_init.sql`, `002_add_users_client_role.sql`. Раннер `runMigrations.js` применяет `.sql`-файлы по алфавиту и помнит применённые в `schema_migrations` (повторный запуск безопасен). Сброс `reset.js` удаляет файл БД вместе с `-wal`/`-shm` и применяет миграции заново; в production запрещён. Бэкап `backup.js` — `VACUUM INTO` + хранение последних 14 копий.
- Сид `seed.js`: 3 пользователя (`admin`/owner, `master`/master, `client`/client — только bcrypt cost 12), 3 мастера (Екатерина, Анна, Ольга-бровист), 5 услуг, график вт–сб 10:00–20:00, 2 клиента, 3 записи на ближайшие рабочие дни (`confirmed`/`wait`, источники `web`/`telegram`). Идемпотентен: повторный запуск создаёт 0 строк. В `production` сид запрещён.
- Верификация на машине без Node: миграции и сид прогнаны Python-эквивалентами, которые исполняют **те же `.sql`-файлы**, пароли хешируются реальным bcrypt; файл `backend/data/nogotki.db` — настоящий SQLite, сервер поднимет его как есть.
- Сверка схемы с фактической БД: все 11 таблиц, поля, индексы и ограничения соответствуют `docs/db-schema.md`; `schema_migrations` — намеренная служебная таблица раннера.
- Документация: `docs/database.md` — живой документ «как устроена БД, какие сложности решали, требование к Node, правило ведения» (обновляется вместе с кодом).

**Сложности и решения.**
- **Внешние ключи в SQLite не включены по умолчанию** → `PRAGMA foreign_keys = ON` выполняется при каждом подключении в `connection.js` (не в миграции). Проверено: `master_id = 9999` отклоняется, при выключенном PRAGMA — проходит.
- **`node:sqlite` без метода `.backup()`** → консистентная копия через `VACUUM INTO`.
- **Даты в SQLite** → единый локальный ISO-текст; сортировка `ORDER BY` совпадает с хронологией.
- **Дубли при повторном сиде** → проверки существования перед каждой вставкой (`seed.js`); подтверждено двумя запусками (второй — 0 строк).
- **Пароли в открытом виде** → сид хеширует `bcrypt.hashSync(password, 12)`; по всей БД открытых паролей нет.
- **Локально нет Node** → верификация Python-эквивалентами на тех же миграциях (`pip install bcrypt`).

## Backend (Node.js): HTTP API сервиса записи

**Когда:** после базы данных — поверх неё собран HTTP API (Express) строго по `docs/db-schema.md`.

**Что сделано.**
- Решения (уточнены у владельца): время в БД — локальное салона, API принимает/отдаёт **UTC ISO с поясом** (`2026-09-25T08:00:00Z`; наивное время отвергается с 400); **Express** как HTTP-фреймворк; разрешена миграция `003` (`slot_holds` + `clients.user_id`).
- Миграция `003_api_slot_holds_clients_user.sql`: таблица `slot_holds` (удержание слота на время оформления, TTL 10 минут, статусы `active/used/canceled`, `token_hash` с UNIQUE, частичный UNIQUE `(master_id, starts_at) WHERE status='active'` против гонки) + `ALTER TABLE clients ADD COLUMN user_id` (FK → users, UNIQUE). Верифицирована Python-эквивалентами на свежей базе (3 миграции подряд) и на копии сид-базы (ALTER на заполненной таблице).
- Структура API:
  - `src/config.js` — конфигурация, `AUTH_SECRET`, `AUTH_TTL_SECONDS` (обязательны для работы);
  - `src/lib/` — `time` (конвертация UTC ↔ локальное салона), `validate` (проверка входных данных до БД, ошибки со `status=400`), `tokens` (JWT-подобные HMAC-SHA256 без внешних библиотек), `http` (async-обёртка и формат ответов), `availability` (вычисление свободных слотов на лету);
  - `src/middleware/auth.js` — `issueToken`, чёрный список `jti` при выходе, `authRequired`, `requireRole(...roles)`;
  - `src/repo/queries.js` — единый слой доступа (подготовленные выражения, сериализация ответов без паролей/чужих ПДн, суммы в копейках, время наружу в UTC);
  - `src/routes/` — `auth` (register/login/logout), `catalog` (services/masters), `holds` (slots, удержание слота), `bookings` (создание по удержанию или с проверкой слота, просмотр, детали, перенос, отмена), `admin` (все записи, CRUD услуг и мастеров — только `owner`);
  - `src/app.js` — сборка Express (JSON-парсер, маршруты, 404, центральный обработчик ошибок); `src/index.js` — запуск, boot из `startup.js`, фоновая чистка истёкших удержаний раз в минуту.
- Свободные слоты: отдельной таблицы нет — считаются из `master_schedule − bookings − work_blocks − studio_closures − slot_holds` с учётом суммарной длительности выбранных услуг (§7.1 `db-schema.md`).

**Сложности и решения.**
- **Задвоение записи по одному токену удержания** → превращение hold в запись атомарно: в одной транзакции `markHoldUsed` (возвращает число изменённых строк; если 0 — удержание уже взято, 409) + `INSERT bookings`.
- **Гонка двух клиентов за один свободный слот** → частичный UNIQUE-индекс `idx_holds_active_slot` на `slot_holds` (`master_id, starts_at WHERE status='active'`); в `POST /holds` перехватывается UNIQUE-нарушение и возвращается 409 `SLOT_CONFLICT`.
- **Вход без пароля наружу** → `publicUser`/`serializeBooking` отдают только нужные поля; хеши паролей и чужие телефоны не сериализуются.
- **`req.body` отсутствует у запросов без JSON-тела** → middleware приводит `undefined` к `{}`.
- **Локально нет Node** → статическая сверка (экспорты/импорты, права доступа по `router.method`), целостность схемы — Python-эквивалентами; реальный запуск — на машине с Node: `npm install`, `AUTH_SECRET` в `backend/.env`, `npm run start:check`, `npm start`.

## Backend (Node.js): защита от пересечения записей — триггеры, транзакции, признак наложения

**Когда:** после сборки HTTP API, по запросу владельца — закрыть риск «двойной записи» на один слот.

**Что сделано.**
- Миграция `004_bookings_overlap_triggers.sql`: защита «в базе» — триггеры `trg_bookings_no_overlap_insert` и `trg_bookings_no_overlap_update` отклоняют запись, пересекающую активную запись мастера (`b.starts_at < NEW.ends_at AND b.ends_at > NEW.starts_at`; вплотную допустимо; `canceled` не учитываются). Требуемое ТЗ «отменённая запись не блокирует слот» противоречило старому `UNIQUE (master_id, starts_at)`, поэтому таблица `bookings` пересоздана: жёсткий UNIQUE заменён частичным `idx_bookings_active_start ... WHERE status != 'canceled'`.
- Транзакции создания/переноса переведены на **`BEGIN IMMEDIATE`** (`connection.js`): блокировка на запись берётся сразу, а не на первой вставке. Гонка «оба прочитали слот свободным» заканчивается ошибкой триггера у второго и 409, а не задвоением.
- `runMigrations.js`: на время применения файлов отключается `PRAGMA foreign_keys` (пересоздание `bookings` с DROP/ALTER безопасно для FK `payments → bookings`), после прогона включается обратно.

- Миграция `005_booking_force_override.sql`: колонка `bookings.force_override` (0/1) — **признак осознанного наложения**. Ставит признак только роль `owner`; триггеры и частичный UNIQUE пропускают записи с признаком; созданная поверх запись дальше ведёт себя как обычная и блокирует других; частичный UNIQUE расширен условием `AND force_override = 0`.

(wantForce ?? 0) : 0;` — `client`/`master` могут передать `force_override` в теле, сервер его **не читает** (значение игнорируется, а не отклоняется — клиент не получает подсказки о существовании такой возможности). Кроме того, `owner` создаёт запись для существующего клиента по `client_id` (раньше роль `owner` в POST вообще падала с 403 «профиль не найден»).

## Backend + фронт: несколько услуг в одной записи (миграция 008)

**Когда:** 2026-09-27. Закрывает блокер из предыдущего раздела: фронт умел выбрать комплекс, а API принимал только одну услугу (`400 HOLD_MISMATCH` на подтверждении). Схема и API менялись по прямому разрешению владельца («да, правь»).

**Что сделано (схема).** `backend/src/db/migrations/008_booking_services.sql`:
- `booking_services` (`booking_id`, `service_id`, `position`, `price_kopecks`, `duration_minutes`) — набор услуг записи со **снимком** цены и длительности на момент записи, порядок выбора клиентом; `ON DELETE CASCADE` от записи, `RESTRICT` от услуги; существующие записи переносятся `INSERT … SELECT` по `bookings.service_id` — миграция ничего не теряет и обратима восстановлением файла БД.
- `hold_services` (`hold_id`, `service_id`) — набор услуг удержания: без него комплексы 120+90 и 105+105 (одинаковые 210 минут) считались бы одним и тем же удержанием.
- `bookings.service_id` остался **первой** услугой: старая статистика, админка, `seed.js` и бот продолжают работать без правок.

**Что сделано (код).**
- `repo/queries.js`: `servicesOfBooking`, `bookingServicesMap` (пакетная выборка без N+1), `createBooking({ serviceIds })` со снимком цены/длительности, `createHold`/`holdServiceIds`, `serializedBooking`. `serializeBooking` отдаёт прежнее поле `service` (первая услуга) + новый `services` + `total_price_kopecks` + `total_duration_minutes`. Сумма в дашборде (`statsDashboard`) считается по всем услугам записи, а не по одной.
- `routes/bookings.js`: `POST` принимает `service_ids` (новое) или `service_id` (прежнее, одна услуга); пустой набор → `MISSING_SERVICES`, дубликаты отклоняются валидатором; все услуги должны быть активны и выполняться мастером (иначе `MASTER_SERVICE_MISMATCH` со списком отсутствующих). `ends_at` = начало + сумма длительностей. Удержание сверяется по **набору** услуг без учёта порядка (`HOLD_MISMATCH`), с откатом на сверку по длительности для удержаний, созданных до миграции. `PATCH /bookings/:id` при смене мастера проверяет весь набор и использует суммарную длительность.
- `routes/holds.js` сохраняет `service_ids` в удержание; `routes/admin.js` считает занятость услуги по обеим таблицам (удаление услуги блокируется, если она вторичная в чьей-то записи) и предлагает свободные слоты по суммарной длительности комплекса.

## Проверка шага «Время»: занятые окна не исчезают (Booking 04)

**Когда:** 2026-09-29. Задача от владельца: пункт 2 промпта проверить отдельно. Соблазн просто не показывать занятое время велик, и модель часто так и делает. Но клиент, который видел свободное окно в 15:00 минуту назад, не поймёт, куда оно делось, если оно исчезнет из списка. Занятое время должно быть видно и недоступно — как в прототипе.

**Что было не так.** Сервер отдавал сетку целиком и правильно: `cells[]` со `state: free|busy|past`, `kind` и `ends_at`, `reason` — `day_off` / `too_long` / `past` / `booked`. Проблема была на экране и в двух смежных местах:

- **Сетка исчезала вместе со свободными окнами.** `renderSlots()` при `free.length === 0` прятал `#slotList` и рисовал на его месте блок Booking 03a. Ровно тот случай, о котором предупреждает владелец: клиент открыл день, увидел свободное 15:00, кто-то занял его, `loadSlots()` перезапросил день — и 15:00 просто пропало. Теперь сетка рисуется всегда, когда сервер её вернул, а блок 03a уезжает **под** неё (`#slotNote`). Без сетки остаётся только блок там, где сетки и не могло быть: выходной и визит длиннее рабочего дня.
- **`next_free` показывал не ближайшее свободное время, а самое дальнее.** В `rangeAvailability()` проход с конца месяца был написан как `list[i].next_free = list[i + 1].next_free || (list[i + 1].slots_count ? … : null)`. Уже посчитанный `next_free` следующего дня короткозамыкал `||`, и проверка «есть ли окна в самом следующем дне» не выполнялась: для 02.10 с десятью свободными окнами API отдавал 08.10, пропуская 03.10 и 06.10. Порядок условий перевёрнут — теперь сначала сам следующий день, и только если в нём окон нет, наследуем найденное для него.
- **409 на удержание шёл без `nearest_free`.** `POST /api/holds` отдавал `SLOT_CONFLICT` с одним только текстом, хотя `web/booking.html:renderConflict()` ждёт `nearest_free`. Экран №26 «Ближайшее свободное время» из карты экранов при конфликте на шаге «Время» не появлялся никогда — только красная плашка. `sendSlotConflict()` теперь принимает код, и оба конфликта (`SLOT_BUSY` на записи, `SLOT_CONFLICT` на удержании) отдают ближайшие окна; `web/js/api.js` больше не привязан к одному коду.
- **Восстановленный из черновика слот не проверялся на `free`.** Сравнение шло по всем `cells`, поэтому занятое или прошедшее окно оставалось выбранным: в резюме и под сеткой показывалось время, которого на сетке уже нет.

**Что сделано в `web/booking.html`.**
- Разделены зоны в разметке: `#slotState` (загрузка/ошибка, над сеткой), `#slotList` (сетка), `#slotLegend` (легенда), `#slotNote` (блок 03a, под сеткой), `#slotResult` (конец визита). Всё, что живёт под сеткой, сбрасывается вместе с ней — `clearSlotExtras()`.
- `renderCell()` вынесена отдельно: свободная ячейка — кнопка, `busy` — видимая зачёркнутая с причиной в `title`, `past` — видимая приглушённая с подсказкой «Это время уже прошло». Легенда под сеткой («занято / уже прошло / свободно») показывается, только если в сетке есть что объяснять.
- Три состояния шага «Время» теперь заведомо разные: индикатор; сетка с кликабельными окнами; сетка целиком зачёркнутая + блок с причиной («Все окна этого дня уже заняты») и ближайшим свободным временем. Ошибка сети — четвёртое, отдельное.
- Подпись под сеткой: «Начало в 14:00 · визит закончится в 15:30 · 1 ч 30 мин» — начало, конец и длительность берутся из `starts_at`, `ends_at` и `duration_minutes` ответа. Сложение длительностей в браузере убрано (раньше строка повторяла конец дважды: «окно 14:00 — 15:30 · закончится в 15:30»).
- `web/css/app.css`: `.slots__legend` и `.slots__key` — цвета только токенов `web/tokens.css`.

**Проверка.** Живой API — 30 проверок: `cells` с `ends_at` и `duration_minutes`, `busy` с `kind` и обязательным исключением из `slots[]`, полностью занятый день (`cells` непустая, `reason=booked`), выходной (`day_off`, `cells` пустая, день есть в сводке месяца), прошедшие дни в сводке без окон, `too_long` по `duration_minutes=700`, `next_free` на пяти соседних днях плюс `null` на последнем дне диапазона, `hold`-ячейка и 409 с `nearest_free`. ## Веб-фронтенд: панель владельца (`web/admin.html`)

**Когда:** 2026-09-29. После закрытия кабинета клиента владельцу негде было смотреть записи студии: рабочий `web/` был целиком клиентским сайтом, а в прототипе панель была статичной вёрсткой на моках.

**Что сделано в `web/admin.html`.**
- Дашборд из `GET /api/admin/stats`: всего записей, активных, сумма активных (считает сервер по `booking_services`), мастеров.
- Таблица всех записей студии из `GET /api/admin/bookings`: дата-время, клиент с телефоном, услуги, мастер, сумма и статус — всё из ответа, суммы и длительности через `api.servicesOf()` от серверных `total_price_kopecks` / `total_duration_minutes`.
- Фильтры: статус, мастер, диапазон дат; любое изменение перезапрашивает список, «Сбросить» очищает. Правая граница даты уезжает как начало **следующих** суток, потому что в API `starts_at < to`. Первый вариант считал прибавление суток в UTC и на `+03:00` съедал день назад — «по 1 октября» не показал бы визиты, начавшиеся в 23:30; теперь сутки считаются по календарной дате.
