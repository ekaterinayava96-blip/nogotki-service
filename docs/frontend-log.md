# Журнал подключения экранов

Собрано по фактическому коду `web/` (клиентский контур) и `web/admin/`
(раздел администратора). Один экран — одна строка или группа строк одного файла.
Названия экранов в прототипе — по
[`prototype-connection-map.md`](prototype-connection-map.md) и
[`ui-map.md`](ui-map.md); поля ответа выписаны по месту их использования в коде.

Прототип — 5 страниц: `index.html`, `booking.html`, `success.html`,
`appointments.html`, `admin.html`. Разделы 1–8 — клиентский контур, раздел 12 —
раздел администратора.

Общее для всех клиентских экранов: `GET /api/auth/me` вызывается из
`web/js/header.js` на каждой странице и по `user.roles` решает, какие ссылки
показывать в шапке (клиенту — «Мои записи», владельцу — «Панель владельца» на
`/admin`). Ошибки API всегда показываются текстом в блоке `#error`
(`web/js/api.js`).

## 3. Запись — общий экран

| Поле | Значение |
|---|---|
| **Экран в прототипе** | `prototype/booking.html` — пошаговый флоу «Услуга → Мастер → Дата → Время → Контакты» |
| **Файл проекта** | `web/booking.html` |
| **Что показывает** | Пять шагов с индикатором прогресса, резюме «Ваша запись» с кнопками «Изменить» у каждой строки, состояние «войдите, чтобы записаться» без сессии, режим переноса записи |

### 3.1. Шаги 1–2: услуги и мастер

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | `GET /api/services`, `GET /api/masters?service_ids=<через запятую>` |
| **Поля ответа** | услуги: `id`, `name`, `description`, `price_kopecks`, `duration_minutes`; мастера: `id`, `name`, `role`, `experience_years`, `photo_path`, `services[].id` |

### 3.2. Шаг 3: дата

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | `GET /api/masters/:id/availability?date_from=…&date_to=…&service_ids=…&step_minutes=60` |
| **Поля ответа** | `days[].date`, `days[].slots_count` (точка «есть окна»), `days[].is_past`, `days[].is_workday`, `days[].reason` (текст в подсказке дня), `days[].duration_minutes` и `days[].window.start_minutes` / `.end_minutes` (для объяснения «окно короче визита») |

Границы месяца и сетка календаря считаются на клиенте; доступность дня приходит
из `days[]`.

### 3.3. Шаг 4: время

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | `GET /api/masters/:id/slots?date=YYYY-MM-DD&service_ids=…&step_minutes=60` |
| **Поля ответа** | `cells[].starts_at`, `cells[].ends_at`, `cells[].state` (`free` / `busy` / `past`), `cells[].kind` (причина занятости — в подсказке), `duration_minutes`, `reason`, `window` |

Подпись «визит закончится в …» собирается из `cells[].ends_at` и
`duration_minutes` ответа.

### 3.4. Шаг 4: «свободных окон нет» (`ui-map.md` №30)

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | те же `availability` и `slots`; ничего дополнительно не запрашивается |
| **Поля ответа** | `reason`, `duration_minutes`, `window` — текст причины; `days[].next_free` (`date`, `starts_at`) из уже загруженного месяца — ближайшее свободное время |

### 3.5. Шаг 5: подтверждение

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | `GET /api/auth/me` — предзаполнение формы |
| **Поля ответа** | `user.client_name`, `user.client_phone`, `user.roles`, `user.username` |
| **Эндпоинты — кнопки** | `POST /api/holds` при входе на шаг; `DELETE /api/holds/:id` при уходе на другой шаг; `PATCH /api/auth/me` — только если клиент правил поля; `POST /api/bookings` с `hold_token` |
| **Поля ответа кнопок** | `POST /api/holds` → `hold_id`, `token`, `starts_at`, `expires_at` (по `expires_at` считается таймер удержания: обычный вид, «меньше минуты», «время вышло»); `PATCH /api/auth/me` → `user` с обновлёнными `client_name` и `client_phone`; `POST /api/bookings` → `booking.id` |

### 3.6. Шаг 5: конфликт «слот занят» (`ui-map.md` №26)

| Поле | Значение |
|---|---|
| **Эндпоинты — данные** | ответ 409 на `POST /api/holds` или на `POST /api/bookings` |
| **Поля ответа** | `error.message` — текст конфликта показывается без пересказа; `error.nearest_free[].starts_at` — кнопки ближайших свободных окон |

### 3.7. Перенос записи (режим `?booking=<id>`)

| Поле | Значение |
|---|---|
| **Экран в прототипе** | нет — режим добавлен при вёрстке (`ui-map.md` №23) |
| **Что показывает** | Прежнее время отдельной панелью, шаги 1–2 скрыты, услуги и мастер зафиксированы, кнопка «Перенести запись» |
| **Эндпоинты — данные** | `GET /api/bookings/:id`, затем те же `availability` и `slots` |
| **Поля ответа** | `booking.starts_at`, `booking.ends_at`, `booking.master` (`id`, `name`, `role`), `booking.services[]` (по `id` восстанавливается набор услуг) |
| **Эндпоинты — кнопки** | `PATCH /api/bookings/:id` с `starts_at` |
| **Поля ответа кнопок** | `booking.id` |

| Поле | Значение |
|---|---|
| **Экран в прототипе** | нет — экрана в прототипе не было, он добавлен при вёрстке |
| **Файлы проекта** | `web/login.html`, `web/register.html` |

Формы входа в разделе администратора нет: вход общий, клиентский. На страницах
`web/admin/*.html` поля пароля нет — это проверено.

## 9. Общие для клиентских экранов решения

| Что | Решение |
|---|---|
| Сессия | httpOnly-кука `nogotki_session`, токен на клиенте не хранится; `GET /api/auth/me` — единственный источник пользователя и его ролей |
| Суммы и длительности | Берутся из ответа (`price_kopecks`, `total_price_kopecks`, `duration_minutes`, `total_duration_minutes`) и не пересчитываются на клиенте, кроме промежуточных итогов на шагах выбора |
| Время | API отдаёт UTC, экран показывает салонное время UTC+3 через `window.api.fmt/hour/day`; «сегодня» считается по дате салона, а не по часам браузера |
| Ошибки | Текст ответа API показывается в `#error` без пересказа; технические детали наружу не выходят (обработчик ошибок в `backend/src/app.js` прячет их для 5xx) |
| Экраны из карты, которых нет | Экран «Обратная связь» (`ui-map.md` №28) в клиентской части не свёрстан: `GET/POST /api/feedback` используется только панелью владельца |

## 10. Что по ходу вёрстки пришлось чинить

### 10.1. Логика

| Что было не так | Как исправили |
|---|---|
| `web/js/cancel.js`: `POST /api/bookings/:id/cancel` уходил в момент открытия окна подтверждения, а не по кнопке «Отменить запись». Клиент успевал прочитать меньше секунды, а нажатие «Не отменять» отмену уже не останавливало — запись всё равно становилась `canceled` | Запрос перенесён внутрь обработчика `#cancelConfirm`. Пока окно открыто, запись остаётся активной. Заодно кнопка восстанавливает подпись и снимает `disabled` при каждом открытии: раньше повторное открытие показывало «Отменяем…» на заблокированной кнопке |

### 10.2. Узкий экран

| Что было не так | Как исправили |
|---|---|
| Шапка: `.nav__links { display: none }` — на телефоне пропадали «Услуги и цены», «О студии» и «Мои записи», попасть в кабинет было нечем | Добавлена кнопка ☰, которая раскрывает панель со всеми ссылками и кнопкой «Записаться». Логотип и блок входа остаются в строке шапки. Панель — вне потока, поэтому шапка от неё не растёт; закрывается по ссылке, клику вне и Escape |
| Сетки `.grid` с `minmax(280px, 1fr)` не помещались в 320px и уводили всю страницу в горизонтальную прокрутку | На узком экране одна колонка; боковые поля контейнера 24px → 16px |
| Сетка слотов на телефоне: окна мелкие, попасть в них пальцем трудно | Две колонки, кнопка ~58px по высоте |
| Ячейки календаря были квадратными и на 360px выходили 27px | `aspect-ratio` отключён, высота 48px |
| Шаг-индикатор: пять шагов с подписями переносились, подписи наезжали друг на друга | Пять равных колонок, цифра над подписью, разделители убраны, длинная подпись переносится внутри своей колонки |
| Панель с итогом и кнопкой «Далее» не держалась под рукой — длинный список услуг приходилось прокручивать заново | `position: sticky; bottom: 0` с непрозрачным фоном. Ограничение по своему шагу не даёт ей закрыть резюме под ним |
| Календарь был только на шаге «Дата»: чтобы сменить день, нужно было уйти на шаг назад и потерять сетку слотов | На узком экране тот же элемент календаря переносится в контейнер шага «Время» над сеткой. Элемент перемещается, а не копируется, поэтому выбранная дата, состояние дней и обработчики кликов сохраняются; на широком экране календарь остаётся на шаге «Дата» |
| Окно подтверждения отмены не помещалось на невысоком экране: текст правила выдавливал кнопки | Окно ограничено по высоте экрана (`dvh`), текст прокручивается внутри, кнопки закреплены внизу и всегда видны. Само тело окна получило класс `.modal__body` |
| Карточки записей: дата и статус не помещались в шапку карточки | Шапка переносится, дата переносится по словам, кнопки действий тянутся на всю ширину |
| Формы входа и страница «Запись создана» не в `.container` — поля прижимались к краям экрана | Боковые отступы 16px на узком экране |

### 10.3. Настольная версия

Правки велись только внутри `@media (max-width: 767px)`. Изменения базовых
правил в шапке (`.nav__inner`, `.brand`, добавлены `.nav__menu`,
`.nav__toggle`) не сдвинули настольную вёрстку: координаты и размеры шапки,
календаря, сетки слотов, карточек, сводки и модалки сверены с исходным CSS и
совпадают.

### 12.1. Записи дня и действия администратора

| Поле | Значение |
|---|---|
| **Экран в прототипе** | `prototype/admin.html`, блок «Заявки на запись» (таблица: услуга, клиент, дата и время, сумма, статус) |
| **Файлы проекта** | `web/admin/bookings.html` + `web/js/admin-bookings.js` |
| **Что показывает** | Записи выбранного дня по студии: салонное время (UTC+3), клиент с телефоном, мастер, услуги с суммой и длительностью, статус. Пометки строки: «Два визита на это время» с пояснением, «переносён с … (сделал …)», «отменил …: причина». Отменённые строки остаются в списке. Сверху — переключение дат (стрелки, поле даты, «Сегодня») и фильтр по мастеру, внизу — итог дня |
| **Эндпоинты — данные** | `GET /api/admin/bookings/day?date=&master_id=`, `GET /api/admin/masters`, слоты для переноса — `GET /api/masters/:id/slots?date=&service_ids=` |
| **Эндпоинты — кнопки** | `PATCH /api/admin/bookings/:id`, `PATCH /api/bookings/:id`, `POST /api/bookings`, `GET /api/admin/bookings/:id/moves` |

**Почему перенос сначала не работал.** Три ошибки в `admin-bookings.js`, все
найдены прогоном страницы без браузера (скрипт с поддельным DOM и настоящими
запросами к живому API):

| Ошибка | Из-за чего перенос ломался |
|---|---|
| `load()` возвращал `undefined` | Отдавал `.then(render)`, а `render()` ничего не возвращает. Дальше `data.bookings` кидал ошибку, `__bkList` оставался пустым, и по кнопке не находилась запись для переноса |
| Дата в форме считалась неверно | `window.api.day()` отдаёт «ДД.ММ.ГГГГ», а разворот порядка давал «ГГГГ.ММ.ДД». `<input type="date">` такой формат не принимает — поле молча оставалось пустым, слоты не грузились |
| Обработчик клика падал на не-`button` | `ev.target.closest('button')` давал `null` при клике по строке или бейджу, обработчик выходил молча |

`openMove()` больше не перезапрашивает день перед открытием формы: список и так
свежий, а лишний запрос ронял `__bkList`. Слоты в форме запрашиваются по набору
услуг **самой записи**, иначе мастеру предлагались бы окна не той длительности.
Если на выбранный день записей нет, страница показывает ближайший день, где они
есть, и говорит об этом — пустой список без пояснения выглядит как поломка.

**Актуальность данных на странице.** Страница запрашивала список один раз — при
загрузке и при смене дня или фильтра. Клиент тем временем отменял запись у себя
в кабинете, и панель продолжала показывать её активной: на экране был старый
снимок, а не ошибка сервера. Свежим запросом к `/api/admin/bookings/day`
статус возвращался верным сразу.

| Как обновляется | Когда |
|---|---|
| Таймер | Каждые 30 секунд |
| Возврат на вкладку | `visibilitychange` — список наверняка устарел |
| Фокус окна | `focus` |
| Кнопка «Обновить» | Рядом с фильтрами |
| Действие администратора | После подтверждения, переноса, отмены, записи поверх занятого |

Фоновое обновление не трогает открытую форму переноса и не затирает сообщение о
успешном действии. Рядом с итогами дня стоит штамп «обновлено в ЧЧ:ММ», по нему
видно, что данные свежие.

**Вёрстка таблицы записей.** Общая `.adm-table` раздаёт ширину по содержимому
каждой строки, поэтому длинная причина отмены или перечень услуг растягивали
колонки по-разному и столбцы «прыгали» от строки к строке. Для страницы записей
заведена `.adm-table--bookings`:

| Что | Зачем |
|---|---|
| `table-layout: fixed` и ширина всем шести колонкам | Столбцы перестали зависеть от содержимого. Если хоть одну оставить `auto`, при `fixed` ей доставался ноль — колонка схлопывалась и содержимое наезжало на соседнюю |
| `min-width` и `overflow-x` обёртки `.adm-table-wrap` | На узком экране таблица прокручивается внутри себя, страница не уезжает вбок |
| Пометки в `.adm-marks` без `<br>` | `.adm-sub` и `.badge` блочные: `<br>` после них давал пустую строку и растягивал ячейку по вертикали |
| `.adm-when > b { white-space: nowrap }` | Время «10:00–11:30» не рвётся, а пометки под ним переносятся. Раньше `nowrap` стоял на всей ячейке, и длинная причина отмены вылезала за край |
| `.adm-actions__row` — `flex` с переносом | Три кнопки в одну строку не помещались; теперь переносятся. Общий `.adm-actions { white-space: nowrap }` для этой таблицы перекрыт |
| `.adm-table--bookings .badge { white-space: normal }` | Бейдж «Два визита на это время» длиннее любой колонки, но это единственное длинное слово — переносить нечего, поэтому колонку состояния расширили до 140px |

Замеры сделаны в headless Chrome через CDP на пяти ширинах — 1920, 1440, 1024,
768 и 390. На всех: 0 ячеек с вылезшим текстом, 0 расхождений столбцов с
заголовком, страница не прокручивается вбок, все строки с шестью ячейками.
Отдельно проверено открытие формы переноса на 1440 и 390: ни одного элемента за
правой границей окна. Функциональная логика не менялась — правка только в
разметке ячеек и CSS.

**Часовой пояс.** Отдельный эндпоинт «на день» раньше не было: панель брала общий
список и фильтровала по `from`/`to`, и границы счётчика и строк разъезжались.
Теперь день приходит как `YYYY-MM-DD`, границы считаются по полуночи салона, а
время рисуется через `window.api.hour()` — тот же перевод UTC → UTC+3, что на
клиентских страницах. Ответ отдаёт `timezone_offset_minutes`, чтобы экран не
угадывал смещение.

## 13. Вход через внешний сервис (Яндекс)

### 13.1. Что добавлено

Кнопка «Войти через Яндекс» — на экранах входа, регистрации и восстановления
пароля. Аккаунт может быть создан при первом входе: пароля у него нет, роль
всегда `client`. Если аккаунт с такой почтой уже есть, второй не создаётся —
внешний вход привязывается к существующему, и человек входит обоими способами.

В прототипе кнопки не было: внешний вход не входил в первоначальный план.
Оформлена существующими классами `btn--secondary`, размеры и цвета — из
`web/tokens.css`, отдельного визуального стиля не заводили.

| Что | Как |
|---|---|
| Миграция `012` | `users.password_hash` стал NULLABLE, добавлены `email`, `provider`, `provider_id` и два уникальных индекса |
| `POST /api/auth/external/yandex` | Принимает почту и имя, ищет по почте, создаёт или привязывает аккаунт, выдаёт свой токен |
| Роль | Всегда `client`. Тело запроса не читается, другую роль этот путь выдать не может |
| Токен | Свой, по тем же правилам, что при обычном входе: те же сроки жизни, SHA-256 в `auth_sessions`, та же кука. Токен Яндекса не сохраняется |
| `POST /api/auth/password/forgot` | Раньше эндпоинта не было — экран получал 404 |

Роли `user` в проекте нет: клиент называется `client`, и `user_roles` ограничен
`CHECK (role IN ('owner','master','client'))`. Заводить второе имя для той же
роли не стали.

### 13.2. Заглушка и почему её нельзя оставлять на сервере

> **Перед публикацией заглушку нужно выключить.**

Приложение в Яндексе **не зарегистрировано**: постоянного адреса, на который
Яндекс вернул бы пользователя, нет, поэтому настоящий обмен кодами невозможен.
Собрана только наша часть входа, а вместо обращения к Яндексу подставляется
заглушка — она берёт почту и имя из настроек и пускает в аккаунт **без проверки
у Яндекса**.

Пока в `.env` стоит `YANDEX_STUB=1`, тестовым входом может воспользоваться
любой, кто знает эти значения. Управляется только настройкой, код править не
нужно:

| Переменная | Смысл |
|---|---|
| `YANDEX_STUB` | `1` — заглушка включена, `0` — выключена. По умолчанию выключена |
| `YANDEX_STUB_EMAIL` | Тестовая почта. Обязательна при включённой заглушке: без неё приложение не стартует |
| `YANDEX_STUB_NAME` | Тестовое имя |
| `YANDEX_CLIENT_ID` / `YANDEX_CLIENT_SECRET` / `YANDEX_REDIRECT_URI` | Настоящее подключение, заполняется после публикации |

Проверка настройки идёт по цепочке: `.env` → `dotenv` в `config.js:10` →
`config.js:66` (`yandexStubEnabled`) → ветвление в `lib/yandex.js:61`.

Место для настоящего подключения — тело одной функции
`fetchIdentityFromYandex()` (`lib/yandex.js:40`). Логика входа не переписывается.

### 13.3. Восстановление пароля для аккаунта без пароля

Сбрасывать нечего: пароля у такого аккаунта нет. Вместо письма показывается
текст «Этот аккаунт входит через Яндекс» и кнопка входа.

| Аккаунт | Ответ | Что видит человек |
|---|---|---|
| Через Яндекс | `200 { method: "yandex" }` | Текст про Яндекс и кнопка |
| Обычный | `501` | «Восстановление не подключено, попробуйте Яндекс или напишите в студию» |
| Не найден | `200 { sent: true }` | То же, что у обычного, — по ответу логины не перебираются |

Письма сервис не отправляет: почтового провайдера в проекте нет. Подменять его
заглушкой не стали — это было бы обещанием, что письмо дойдёт.

### 13.5. Найдено, но не исправлено

Аккаунт, созданный через внешний вход, **не может записаться**: `403
NO_CLIENT_PROFILE`. Нужен телефон, а Яндекс его не отдаёт, а `clients.phone`
обязателен. Выдумывать номер не стали. Варианты: спросить телефон при первой
записи или сделать поле необязательным — решение продуктовое. Клиентская отмена записывает «Отменена клиентом» |
| Перенос — то же посещение | `PATCH /api/bookings/:id` меняет `starts_at` у той же строки. Ни отмены, ни новой записи: `client_id` прежний, поэтому клиент получает одно уведомление |
| След переноса | Таблица `booking_moves`: откуда, куда, у какого мастера, кто перенёс. Пишется **до** движения, иначе «откуда» уже не узнать |
| Запись поверх занятого | Только роль `owner` и в два шага. Первый запрос с `force_override=1` получает 409 с `can_force` и подсказкой — **запись не создаётся**. Второй с `confirm=1` создаёт |
| Проверка занятости не отключается | Она срабатывает на обоих шагах; `force_override` её не выключает, а лишь разрешает второй шаг. Клиент и мастер поле `force_override` игнорируют намеренно |
| Пометка о двух визитах | `conflict_note` пишется при создании наложенной записи. Признак двойной записи в списке дня считается на лету (`bookingHasOverlap()`), а не по флагу — иначе запись, созданная до флага, осталась бы незамеченной |

Время освобождения и занятости считает сервер, экран этого не решает. Клиент без
роли `owner` получит 409 и при `force_override=1, confirm=1`.

### 12.3. Услуги и мастера редактируются из админ-панели

Справочники студии больше не правятся в базе вручную: услуги и мастера
создаются, редактируются, включаются и выключаются из раздела `/admin`.

| Поле | Значение |
|---|---|
| **Экран в прототипе** | `prototype/admin.html` — блок «Заявки на запись» с навигацией и блок «Мастера студии» (услуги в прототипе не нарисованы) |
| **Файлы проекта** | `web/admin/services.html` + `web/js/admin-services.js`, `web/admin/masters.html` + `web/js/admin-masters.js` |
| **Что показывает «Услуги»** | Таблица всех услуг, включая отключённые (метка «Отключена»): название, описание, цена, длительность, состояние. Форма добавления и правки: название, описание, цена ₽, длительность мин, чекбокс «активна». У строки — «Изменить», «Включить/Отключить», «Удалить» |
| **Что показывает «Мастера»** | Таблица всех мастеров, включая отключённых: имя, специализация, опыт, число записей, перечень выполняемых услуг, состояние. Форма: имя, специализация, опыт, чекбокс активности и отметки услуг |
| **Эндпоинты — данные** | `GET /api/admin/services`, `GET /api/admin/masters`. Перед каждым действием список запрашивается ещё раз, чтобы узнать текущее состояние строки |
| **Эндпоинты — кнопки** | `POST /api/admin/services`, `PATCH /api/admin/services/:id`, `DELETE /api/admin/services/:id`; `POST /api/admin/masters`, `PATCH /api/admin/masters/:id`, `DELETE /api/admin/masters/:id` |
| **Поля ответа** | услуга: `id`, `name`, `description`, `price_kopecks`, `duration_minutes`, `is_active`; мастер: `id`, `name`, `role`, `experience_years`, `bookings_count`, `is_active`, `services[]`. Ответ удаления: `outcome` (`deleted` / `disabled` / `already_disabled`), `message`, `bookings_count` |

Отключённые строки клиенту не видны, и это делает сервер: `GET /api/services` и
`GET /api/masters` читают только `is_active = 1`. Экраны только показывают их
администратору. В форме мастера отметки строятся по `GET /api/admin/services`,
то есть включая отключённые услуги, — иначе связь с отключённой услугой была бы
не видна и не снимаема.

Клиентский выбор мастера связь уже учитывал: `GET /api/masters` отдаёт
`services[]`, страница записи блокирует мастера, который не делает выбранные
услуги, а `POST /api/bookings` отклоняет такой выбор с `MASTER_SERVICE_MISMATCH`.

### 12.4. Что изменилось в API

| Что | Как |
|---|---|
| `DELETE /api/admin/services/:id` | Отвечает 200 с `outcome` вместо 409. Нет записей — удаляет; есть — отключает и объясняет. Ссылок считает `queries.countBookingsWithService()`: и `bookings.service_id`, и `booking_services.service_id` |
| `DELETE /api/admin/masters/:id` | То же: при наличии записей отключает вместо удаления |
| `price_kopecks` в `POST`/`PATCH /api/admin/services` | `nonNegInt` → `positiveInt`. Нулевая цена означала бы «бесплатную услугу», а нулевая длительность — слот нулевой длины, который сломал бы расписание |

Проверено запросами: пустое и пробельное название, цена `0` и отрицательная,
длительность `0` и отрицательная, отсутствующая и дробная цена — во всех случаях
400 от сервера. Удаление услуги без записей → `deleted`, после него `PATCH` →
404. Удаление услуги с записями → `disabled`, повторный `DELETE` →
`already_disabled`.

### 12.5. Запись хранит цену и длительность услуги на момент оформления

Правило: **цена и длительность, записанные в записи, не меняются при правке
прайса.** Запись — это история, а не настройка: клиент пришёл на ту сумму и на
то время, которые видел при записи.

Где это лежит:

| Где | Что |
|---|---|
| `booking_services.price_kopecks` | Снимок цены на момент оформления |
| `booking_services.duration_minutes` | Снимок длительности на момент оформления |
| `bookings.service_id` | Первая услуга записи, для обратной совместимости |
| Итог записи | `SUM(booking_services.price_kopecks)`, длительность — тоже сумма |

Обе колонки заведены **миграцией 008** — отдельная миграция под эту задачу **не
создавалась**. Значения копируются в момент создания записи
(`queries.createBooking()`):

```sql
INSERT INTO booking_services (booking_id, service_id, position, price_kopecks, duration_minutes)
SELECT ?, id, ?, price_kopecks, duration_minutes FROM services WHERE id = ?
```

`SELECT ... FROM services` — то есть читается текущая строка справочника именно
в момент оформления, и дальше запись от прайса не зависит.

Проверено на живом API: услуга 1000 ₽ / 60 мин → запись на неё → правка прайса
на 9999 ₽ / 15 мин. В уже созданной записи остались 1000 ₽ и 60 мин:
`total_price_kopecks`, `total_duration_minutes` и оба значения в `services[]`.

Что это даёт панели: в `GET /api/admin/bookings` сумма приходит из
`booking_services`, а не из справочника, поэтому переоценка услуги не переписывает
историю выручки, и старый клиент не вдруг получает счёт по новому прайсу.

Следствие для отключения услуги: `DELETE` при наличии записей не удаляет строку,
а отключает (см. 12.2) — иначе вместе с услугой пропали бы и её названия, и суммы
в истории записей.

### 12.6. Уведомления в кабинете

| Поле | Значение |
|---|---|
| **Экран в прототипе** | нет. В папке «Прототип» такого экрана не было, и `ui-map.md` прямым текстом предлагал его убрать из вёрстки. Экран собран по общей системе страниц `web/` |
| **Файлы проекта** | `web/notifications.html`, правки `web/js/header.js`, `web/js/api.js`, стили `.notif` и `.nav__bell*` в `web/css/app.css` |
| **Серверный файл** | `backend/src/routes/notifications.js`, тексты — `backend/src/lib/notifications.js`, таблица — миграция 011 |
| **Что показывает** | Список уведомлений новыми сверху: вид события, когда («2 дня назад»), текст и переход на запись. Непрочитанные подсвешены фоном |
| **Эндпоинты — данные** | `GET /api/notifications` — список **и** счётчик `unread` одним ответом |
| **Эндпоинты — кнопки** | `POST /api/notifications/:id/read` |

**Счётчик в шапке.** Раньше его в шапке не было вообще — ручного числа в разметке
тоже: `header.js` рисовал аватар, имя и «Выйти», и всё. Колокольчик добавлен в
`.nav__auth`, число подставляется из ответа `/api/notifications`. Отдельного
запроса ради счётчика нет, ответ кэшируется на странице: экран уведомлений и
шапка берут одни и те же данные.

**Когда уведомление создаётся.** Только когда событие произошло не по инициативе
самого клиента. Отмена, перенос и запись клиентом уведомлений не дают — клиент
видит результат своей же кнопки.

| Событие | Текст |
|---|---|
| Отмена администратором | «Запись на среду, 13:00 отменена: Мастер заболел, визит переносим. Запись на это время снова свободна — запишитесь заново.» |
| Перенос администратором | «Запись на среду, 13:00 перенесена на четверг, 14:00.» |
| Второй визит на это время (у кого заняли) | «На ваш визит в пятницу, 14:30 записан ещё один клиент. Проверьте, сможете ли вы прийти в это же время.» |
| Второй визит на это время (у кого создали) | «На ваше время в пятницу, 14:30 в студии записан ещё один визит. Проверьте, сможете ли вы прийти в это же время.» |

Проверено на живом API: во всех четырёх случаях текст такой; при самостоятельной
записи, отмене и переносе клиента уведомлений 0. Чужое уведомление отметить
прочитанным нельзя — 404. Почта и внешние сервисы не подключались.

**Наложение через перенос.** Отдельная находка: уведомление `booking_conflict`
приклеивалось только к `POST /api/bookings` (создание новой записи), а админка
создаёт двойные записи **переносом** — `PATCH /api/bookings/:id`. В этой ветке
уведомления не было вовсе, и сам перенос поверх занятого времени не проходил:
`moveBooking()` не выставлял `force_override`, поэтому запись отбивал
`idx_bookings_active_start` и приходил 409 даже с подтверждением.

| Что | Как |
|---|---|
| `moveBooking()` принимает `forceOverride` и `conflictNote` | Подтверждённый перенос поверх занятого помечается, как и создание записи |
| `queries.overlappingBookings()` | Поиск по **пересечению интервалов** (`starts_at < конец AND ends_at > начало`) |
| `PATCH /api/bookings/:id` при `isOwner` | Если визит встал поверх чужого, шлются оба уведомления: пострадавшему («на ваш визит») и перенесённому («на ваше время») |
| Ответ `PATCH` | Добавлено поле `forced` — панель пишет в подтверждении, что время было занято |

**Почему пострадавший оставался без уведомления.** Тот же негодный поиск стоял
и в `POST /api/bookings`: он отбирал записи, чьё **начало** попало в диапазон
новой. Запись, начавшаяся раньше новой и длящаяся через её хвост, в этот диапазон
не попадала — а именно такие чаще всего и перекрываются. На тесте «пострадавший
с 10:00, новая запись с 10:30» уведомление не приходило вовсе. Теперь оба пути
(`POST` и `PATCH`) ищут пересечением интервалов и уведомляют **всех** пострадавших:
длинный визит может перекрыть два коротких.

Типы уведомлений не расширяли: по-прежнему ровно три — `booking_canceled`,
`booking_moved`, `booking_conflict`, и то же ограничение `CHECK` в миграции.

Замечание: форма переноса в панели наполняется `GET /api/masters/:id/slots`,
а он отдаёт только **свободные** окна, поэтому выбрать занятое время в ней
нельзя. Наложение из панели достижимо только через кнопку «Записать клиента на
это время», а она требует выбора клиента — эндпоинта списка клиентов в API нет
(`GET /api/admin/clients` → 404, см. `ui-map.md` §4.1). Это пробел данных, а не
ошибка уведомлений; наполнять его здесь не стали.

### 12.7. Действия администратора с чужой записью

Полный список того, что владелец может сделать с записью другого клиента, и что
после этого видит клиент в своём кабинете.

| Действие | Эндпоинт | Что происходит у клиента |
|---|---|---|
| **Подтвердить** | `PATCH /api/admin/bookings/:id` (`status=confirmed`) | Бейдж «Подтверждена» вместо «Ожидает». Визит остаётся на вкладке «Активные» — время, мастер и услуги те же. Уведомления нет |
| **Выполнена** | тот же `PATCH` (`status=done`) | Бейдж «Выполнена». Визит перестаёт считаться активным. Уведомления нет |
| **Отменить** | тот же `PATCH` (`status=canceled` + `reason`) | Запись **остаётся** и уезжает с «Активных» на «Историю» с бейджем «Отменена» и причиной. Слот мастера освобождается — клиент может записаться заново. Приходит уведомление |
| **Перенести** | `PATCH /api/bookings/:id` (`starts_at`) | Тот же визит с новым временем. Запись одна, второго уведомления нет. Приходит уведомление с двумя датами |
| **Перенести поверх занятого** | тот же `PATCH` (`force_override` + `confirm`) | Клиент видит **две** записи на одно время — это честно, визиты разных людей. В панели обе строки помечены «Два визита на это время». Уведомление получают оба |
| **Записать клиента поверх занятого** | `POST /api/bookings` (`force_override` + `confirm`) | То же: у клиента чужое время появляется второй визит. Уведомления получают обе стороны |

Все действия доступны только владельцу: страницы закрыты `requireOwnerPage`, данные
и изменения — `requireRole('owner')`. Клиент своего кабинета не видит, и его
собственные кнопки («Перенести», «Отменить») работают ровно так же.

Что администратор **не** может: удалить строку записи, создать для клиента вторую
запись в обход подтверждения и выдать себе роль — см. 12.11.

### 12.8. Для каких событий создаются уведомления

Правило одно: **уведомление создаётся, только когда событие произошло не по
инициативе самого клиента.** Клиент отменил или перенёс визит сам — он и так
только что это сделал, сообщать ему не о чем. Типов ровно три, столько же и
значений в `CHECK` миграции 011.

| Тип | Событие | Кто получает |
|---|---|---|
| `booking_canceled` | Отмена администратором | Владелец записи |
| `booking_moved` | Перенос администратором | Владелец перенесённой записи |
| `booking_conflict` | На это время назначен ещё один визит | Обе стороны: кому заняли время («на ваш визит») и чью запись создали («на ваше время») |

Текст пишется при создании и содержит конкретные дату и время, а не общие слова:
«Запись на среду, 13:00 перенесена на четверг, 14:00». День недели ставится в
винительном падеже с маленькой буквы — «на среду», а не «на Среда».

Уведомление не создаётся, если у клиента нет учётной записи: показывать его
некому.

## 14. Резервное копирование базы без участия человека

### 14.1. Что было сломано

Копий базы не существовало. Команда `npm run db:backup` была, механизм
`VACUUM INTO` был, ротация старых копий была — но копий на сервере не лежало
ни одной.

### 14.2. Почему

Копирование вызывалось **только** при `require.main === module`:

```js
if (require.main === module) {
  backup().then(() => db.close());
}
```

Условие истинно исключительно тогда, когда скрипт запустили как отдельную
программу (`node src/db/backup.js`). При обычном старте сервера условие ложно,
и `backup()` не вызывается **никем** — ни одним обработчиком, ни одним таймером
во всём приложении.

Дальше — рассуждение, которое объясняет, почему это прожило незамеченным.
Копирование базы нельзя «включить в коде»: приложение не умеет планировать
события в будущем. Для этого нужен планировщик операционной системы — cron на
Linux, Планировщик заданий на Windows. Такой планировщик был описан **в
комментарии** к файлу, с готовой строкой:

```
30 3 * * * cd /путь/к/backend && sudo -u nogotki /usr/bin/node src/db/backup.js
```

Инструкция выглядела как готовое решение, и её не выполнили. Получилось
недоделанное внедрение: программа исправна, обязательного шага нет, а проверить
было нечем — команда запускается и работает, поэтому всё выглядит здоровым.

### 14.3. Что изменилось

Расписание перенесено внутрь приложения — планировщик ОС больше не нужен.

| Что | Где |
|---|---|
| `startBackupSchedule()` — таймер копирования | `backend/src/db/backup.js` |
| Запуск расписания при старте сервера | `backend/src/index.js` |
| `BACKUP_INTERVAL_HOURS` — как часто, в часах; `0` отключает | `backend/src/config.js`, `.env.example` |
| `BACKUP_KEEP` — сколько копий хранить | там же |
| `BACKUP_ON_START` — копия сразу при старке | там же |

Таймер помечен `unref()`, чтобы не держать процесс, как и таймер чистки
удержаний рядом. Сбой копирования перехватывается и пишется в журнал: теряется
одна копия, а не работающий сайт. Ручной запуск сохранён — он нужен перед
переездом и для копии «здесь и сейчас».

Значения настроек проверяются на старте, а не молча: `BACKUP_INTERVAL_HOURS=abc`
или `BACKUP_KEEP=0` останавливают сервер с внятным сообщением. Иначе опечатка в
`.env` тихо отключила бы страховку — ровно та же беда, что была до правки.

## 15. Проверка прав доступа в HTTP-слое

### 15.1. Что было сломано

Проверки прав в HTTP-слое у проекта не было. Набор `test_role_scenarios.py`
роли проверяет, но проверяет **копию правил**, а не настоящий код:

```python
def api_create_bookings(role, body):
    ...
    if role == "master":
        if not user["master_id"] or master_id != user["master_id"]:
            return (False, "FORBIDDEN", None)
```

Функция заново описывает, кому что можно, прямо на Python, и обращается к
базе, минуя Express. Если в маршруте забыть `requireRole`, этот набор останется
зелёным — он ничего не заметит, потому что проверяет сам себя.

### 15.2. Что сделано

Добавлен `backend/tests/test_access_matrix.py`. Он собирает маршруты прямо из
исходников `backend/src/routes/*.js`, поэтому новый маршрут попадает в
проверку сам — добавлять его в список вручную не нужно.

| Что проверяется | Смысл |
|---|---|
| Аноним не получает 2xx на закрытом маршруте | Главное: забытая проверка видна сразу |
| Клиент не получает 2xx на маршрутах админки | Чужой роль не заходит в чужой раздел |
| Владелец не получает 5xx | Маршрут существует и не падает |
| Гость всё же получает доступ к публичным | Нет обратной проблемы: лишних запретов |
| Страницы панели закрыты без роли | `/admin.html` и разделы |

Публичные маршруты перечислены явно. Непроверенным считается всё, чего в списке
нет: при добавлении маршрута он по умолчанию попадёт под проверку на закрытость.

Тест сам себя убирает: одноразовый клиент регистрируется в начале и удаляется
в `finally` прямой работой с базой, как это делает соседний набор.

### 15.3. Проверено, что набор действительно работает

Набор, который всегда зелёный, бесполезен. Поэтому он проверен на сломанном
коде: с проверки снят `authRequired`, сервер перезапущен, набор прогнан снова.

| Опыт | Результат |
|---|---|
| Все проверки на месте | `ok=121 fail=0` |
| Снят `authRequired` с `GET /api/notifications` | `ok=120 fail=1` — пойман |
| Снят `authRequired` с `GET /api/feedback` | Утечки не вышло: `403`, пойман проверкой роли внутри обработчика |

Второй опыт оказался содержательнее, чем первый. Данные не утекли, потому что
обработчик сам проверяет роль: `hasRole(req.user, 'client')` для гостя даёт
`false` и ответ `403`. То есть у most маршрутов два рубежа — middleware и
проверка внутри. Это хорошо, и объясняет, почему снятие проверки чаще даёт
`500`, а не тихую утечку: код почти везде читает `req.user.id`, и при его
отсутствии падает.

Честное ограничение: этот набор ловит **снятие проверки**, а не утечку как
таковую. Совпадение этих вещей неполное — снятая проверка может дать и `500`,
и `403`. Но и то, и другое набор считает провалом маршрута.

### 15.4. Границы покрытия

- Права на конкретную чужую строку (чужой `:id`) здесь не проверяются: закрытый
  маршрут вернёт `404` ещё до проверки прав. Эти случаи закрывает
  `test_role_scenarios.py`.
- Содержимое ответов не проверяется — важна только код ответа.
- Набор требует поднятого сервера; учётные записи владельца берёт из
  `backend/.env.test`.

### 15.5. Границы решения

Закрыт только тестом, без «запрещено по умолчанию» в самом приложении. Это
осознанный размен: правка теста ничего не может сломать в работающем сервисе,
тогда как заглушка на уровне `app.js` меняет поведение всех маршрутов разом и
может закрыть что-то нужное. Следующая по риску находка — 1.3, формат дат.
