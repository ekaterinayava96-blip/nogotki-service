# Карта клиентских экранов «Ноготочки» (для вёрстки)

Источники: кликабельный прототип `prototype/` (SPA: 5 страниц, экраны-состояния рендерятся `app.js`),
черновой фронт `backend/public/`, код API `backend/src/routes` (папки `server/` в репозитории нет — сервер в `backend/`).

Как читать столбец «Файл»: `prototype/…` — экран уже есть в прототипе; `backend/public/…` — экран есть только в черновом фронте;
`—` — файла нет нигде, экран придётся верстать с нуля (но он нужен по ТЗ).

Основная таблица покрывает ТОЛЬКО клиентские экраны. Панель владельца из прототипа
(`prototype/admin.html`, `/api/admin/*`) вынесена в §3 внизу: рабочий экран `web/admin.html`
сверстан 2026-09-29 отдельно от клиентских.

> По разбору пробелов данных (раздел внизу) из вёрстки убраны: фото услуг, индикатор занятости дня,
> экраны «Профиль» и «Уведомления». Добавлен экран «Обратная связь».
>
> Форма контактов на шаге подтверждения вернулась: пользователь сам попросил
> настоящую форму с `PATCH /api/auth/me` (решение внизу раздела).

## 3. Панель владельца (не клиентский контур)

Клиентский кабинет (№13) закрыт для owner и master: `GET /api/bookings` владельцу
отдаёт **все** записи студии, и в блоке «Мои записи» они читались бы как чужие визиты,
аowner получал бы кнопки отмены и переноса чужим записям. Поэтому записи всех клиентов
смотрит отдельная страница, а в шапке ссылки теперь зависят от роли: клиенту —
«Мои записи», владельцу — «Панель владельца» (`web/js/header.js`).

|---|---|---|---|---|---|---|
| 31 | Панель владельца — дашборд и записи (сверстано) | `web/admin.html` | Цифры (всего/активных/сумма активных/мастеров) и таблица записей студии: дата-время, клиент с телефоном, услуги, мастер, сумма, статус-бейдж, действия. ### Чего в панели нет (осознанно)

| Чего не хватает | Почему |
|---|---|
| Расписание мастеров, работа с услугами и мастерами, отзывы, статистика за период | Эндпоинты `GET/PUT /api/admin/masters/:id/schedule`, `POST /api/admin/masters/:id/work-blocks`, CRUD услуг и мастеров, `GET /api/admin/feedback`, `GET /api/admin/stats` (без периода) в API есть, но на экран не выведены. | Пагинация списка | `GET /api/admin/bookings` отдаёт всё одним ответом, `limit`/`offset` в API нет. На объёме студии (десятки записей) хватает; при росте истории понадобится пагинация в API. |

## Расхождения и решения (бэкенд не трогаем — всё решаем на стороне экрана)

### 1. Экрану не хватает данных

| Находка | Решение | Почему |
|---|---|---|
| Лендинг — фото услуг | Убрать элемент из вёрстки | `GET /api/services` фото не отдаёт (`services.photo_path` в сиде NULL), каталог читается и без картинок; фото мастеров остаются — их отдаёт `GET /api/masters`. |
| Календарь записи — индикатор «занятости дня» | Убрать элемент из вёрстки | `GET /api/masters/:id/slots` отдаёт только свободные слоты, занятость дня API не знает — признак декоративный. Занятость в календаре заменена числом свободных окон из `GET /api/masters/:id/availability` (`slots_count`), а на шаге «Время» занятые окна приходят готовыми `cells` со `state: busy` и `kind`. |
| ~~Шаг «Контакты» — поля «Имя»/«Телефон»~~ | ~~read-only~~ → **сверстана форма с `PATCH /api/auth/me`**, см. §4 | Имя/телефон — данные аккаунта, но в записи участвует другой человек (записывает подругу, коллеге). Read-only не даёт поменять данные для конкретного визита. Эндпоинта правки профиля раньше не было — добавлен `PATCH /api/auth/me`, а `GET /api/auth/me` теперь отдаёт `user.client_phone`, чтобы форма предзаполнялась. |
| Экран «Профиль» | Убрать элемент из вёрстки | Эндпоинтов чтения/правки профиля нет, сценарий записи проходит без него. |
| Экран «Уведомления» | Убрать элемент из вёрстки | Напоминание за 24 часа — функция бота, уведомлений в API/БД нет. |

| Эндпоинт | Зачем | Ответ |
|---|---|---|
| `PATCH /api/auth/me` | Сохранить имя и телефон из формы подтверждения, не заставляя клиента идти в отдельный экран профиля | `{ client: {...}, user: {...} }`, причём `user` несёт обновлённые `client_name` и `client_phone`; 400 `NOTHING_TO_UPDATE`, 400 `INVALID_NAME` / `INVALID_PHONE`, 409 `PHONE_TAKEN`, 403 `FORBIDDEN` |
| `GET /api/auth/me` → `user.client_phone` | Предзаполнить форму. Раньше `user` отдавал только `client_name`, и у клиента без записей взять телефон было неоткуда | Телефон клиента в профиле (`clients.phone`), тот же источник, что `PATCH` |

### 3. Решения по шагам «Дата»/«Время» (Booking 03/03a)

| Вопрос | Решение | Почему |
|---|---|---|
| Кто считает свободные окна | Сервер (`backend/src/lib/availability.js`) | Клиент не знает расписание мастера, записи, блоки и удержания. В браузере остаётся только показ `cells` и `days`; «шаг 60 мин» приходит из запроса и совпадает с сеткой. |
| Прошедшие дни и выходные | Видны, но отключены | Клиент должен видеть, что день есть и почему его нельзя выбрать: подсказка в `title` — «Дата уже прошла» / «У мастера выходной». То же в сетке времени: окно состояния `past` рисуется приглушённым и некликабельным, а не выбрасывается из списка. |
| Полностью занятый будний день | Кликабельный, открывает 03a | Иначе клиент не поймёт, что день был и чем занят, и не увидит ближайшую замену. |
| Занятые окна внутри сетки | Рисуются зачёркнутыми и некликабельными (`state: busy` + `kind` в подсказке) | Клиент, который минуту назад видел в этой же сетке свободное 15:00, не поймёт, куда оно делось, если окно просто исчезнет из списка. Причина в `title` отвечает на вопрос «а кто занял?» (`booking` / `hold` / `block` / `closure`). |
| «Пустая» сетка | Отдельные состояния: загрузка (индикатор), ошибка («Повторить»), нет окон (03a под сеткой) | Пустой список окон без объяснения выглядит как поломка; индикатор не должен мигать пустотой. В состоянии «окон нет» сетка остаётся на экране — см. строку выше; без неё блок 03a показывается только когда сетки и не могло быть (`day_off`, `too_long`). |
| Сохранённый выбор слота | Сбрасывается, если окно больше не `free` | Иначе резюме и подпись под сеткой будут показывать время, которого на сетке уже нет. |
| Конец визита | `ends_at` и `duration_minutes` из ответа API | Длительность набора услуг меняется, клиент пересчитывать её не должен. |
| Текущий месяц | По дате салона (`GET /api/studio` → `today_salon`), не по часам браузера | Клиент в другом часовом поясе иначе увидит лишний день в календаре. |
| Ближайшее свободное время в 03a | `next_free` из уже загруженного месяца | Без дополнительного запроса; если в этом месяце окон нет — кнопка «Показать следующий месяц». Считается проходом с конца месяца: сначала сам следующий день, и только если в нём окон нет — то, что нашлось для него. |

### 4. Решения по шагу «Подтверждение» (Booking 04/04b/05)

| Вопрос | Решение | Почему |
|---|---|---|
| Форма контактов | Настоящая форма, предзаполненная из `GET /api/auth/me`; сохраняется через `PATCH /api/auth/me` только если поля реально изменились | Записываться можно не на себя. Правка профиля в этот момент означает, что данные аккаунта и данные визита совпадают — оба места показывают одно и то же, расхождения не возникает. |
| Незалогинен на шаге 5 | Кнопка «Войти, чтобы записаться» + предупреждение, что без аккаунта запись не сохранится и не попадёт в «Мои записи» | Форме нужен `client_id`; врать нельзя — предупреждаем заранее. |
| Удержание слота | Создаётся при входе на шаг 5 (`POST /api/holds`, 10 мин), снимается при уходе на другой шаг или при выборе другого окна | Клиент ходит по резюме, редактирует контакты и может уйти со страницы. `DELETE /api/holds/:id` освобождает слот немедленно, а не через 10 минут — иначе следующий клиент увидит занятое время из-за брошенной формы. |
| Таймер удержания | Три состояния: обычный, «меньше минуты» (предупреждение), «время вышло» (кнопка «Выбрать время заново») | Клиент не обязан знать про 10 минут, но обязан увидеть, что время кончилось, до нажатия «Подтвердить». Состояние переживает перерисовку. |
| Ушёл со страницы не отпустив hold | `hold` истекает сам за 10 минут | Клиент может закрыть вкладку; `pagehide`/`beforeunload`-запросы ненадёжны, серверная TTL-очистка — единственная гарантия. |
| Конфликт при подтверждении | Блок 04b внутри шага 5: текст из ответа + кнопки `nearest_free` | Клиент уже ввёл контакты; выбрасывать его на шаг 4 — потеря сделанного. Варианты берём только из `nearest_free` ответа — других источников свободного времени нет. |
| Правка контактов при уходе и возврате | Поля сохраняют правку клиента и отправляются при следующем подтверждении; профиль перезаполняется только после успешного PATCH | Клиент уходит «подумать» и возвращается — его введённый номер не должен пропадать. Перезаписывать его данными профиля означало бы, что PATCH ушёл в пустоту, а клиент об этом не узнает. |
| Услуги и итог на экране успеха | Построчно из `services[]` ответа, «К оплате» — суммой этих же цен | Итог на подтверждении и итог на экране успеха должны совпадать, иначе клиент не поверит квитанции. |
| «Запись не найдена» на экране успеха | Отдельный блок с ссылкой в «Мои записи» | Ссылка с `?booking=` попадает в историю и мессенджеры; запись могла быть удалена. |
| Контакт на экране успеха | `client.name` + `client.phone` из `GET /api/bookings/:id` | Показываем контакты, на которые записан визит — то есть те, что были в форме (в т. ч. изменённые), а не текущие данные аккаунта. |

### Что на стороне экрана решить нельзя

- Вывод фото услуг (данных нет в API);
- индикатор занятости дня в прежнем виде (API не отдавал; вместо него — `slots_count` из `GET /api/masters/:id/availability` и готовые `cells` в сетке слотов);
- редактирование профиля целиком (аватара, смены пароля) — эндпоинтов нет; на шаге 5 правятся только имя и телефон, ради которых добавлен `PATCH /api/auth/me`;
- напоминание за 24 часа (функция бота, данных нет).

Первые, второй и последний закрыты удалением блока/экрана из вёрстки (см. таблицы выше) — правок API не требуется. Третий закрыт частично: `PATCH /api/auth/me` добавлен под имя и телефон на шаге 5, остальное (аватар, смена пароля) по-прежнему без эндпоинтов.
