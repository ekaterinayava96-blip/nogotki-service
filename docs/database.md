# База данных бэкенда «Ноготочки» — как она устроена, какие сложности решали

Это живой документ: описывает **фактическое** состояние базы данных бэкенда
(`backend/`, пакет `nogotki-backend`) и логику, по которой она выстроена.
При любых дополнениях/изменениях проекта **этот документ обновляется вместе с кодом**
(см. «Правило ведения» в конце).

Смежные документы:
- `docs/db-schema.md` — полная схема (таблицы, поля, ограничения, индексы) и обоснование решений.
- `docs/prototype-connection-map.md` — карта связей «экран прототипа → данные».
- `AGENTS.md` — паспорт продукта и функции для пользователя/владельца.

---

## 1. Текущее состояние

База — **SQLite 3**, файл `backend/data/nogotki.db` (путь задаётся `DB_PATH`,
по умолчанию относительно `backend/`). Подключается через **встроенный модуль
`node:sqlite`** (`DatabaseSync`) — внешняя библиотека SQLite не используется.

Схема развёрнута миграциями (12 таблиц + 12 именованных индексов). Сводно:

| Таблица | Назначение |
|---|---|
| `services` | каталог услуг (цена в копейках, длительность в минутах) |
| `masters` | мастера студии (имя, специализация, опыт) |
| `studio_info` | контакты студии (одна строка) |
| `master_services` | какие услуги умеет каждый мастер (N:M) |
| `master_schedule` | регулярный график: день недели, минуты начала/конца |
| `work_blocks` | разовые блокировки времени мастера (перерыв, отпуск, больничный) |
| `studio_closures` | дни полного закрытия студии |
| `bookings` | записи клиентов (центральная таблица); признак `force_override` — осознанное наложение администратором |
| `slot_holds` | удержание слота на время оформления (миграция 003) |
| `clients` | клиенты (нормализованы отдельно) |
| `users` | учётные записи для входа + роли списком в `user_roles`; только хеш пароля |
| `user_roles` | роли пользователя списком (`owner`/`master`/`client`), миграция 007 |
| `auth_sessions` | сессии входа: SHA-256 токена, срок, отзыв (миграция 007) |
| `payments` | платежи (предоплата, ЮKassa) |

Дополнительно служебная таблица `schema_migrations` (журнал применённых миграций) —
она есть только у раннера миграций и в схеме §4 намеренно не фигурирует.

Тестовые данные (сид) актуальны на момент написания:
- 3 пользователя: `admin`/owner, `master`/master (привязан к мастерице Екатерине), `client`/client;
- 3 мастера: Екатерина (маникюр и брови), Анна (маникюр), Ольга (бровист);
- 5 услуг; график вт–сб 10:00–20:00 у трёх мастеров;
- 2 клиента, 3 записи на ближайшие рабочие дни (статусы `confirmed`/`wait`, источники `web`/`telegram`).

Подробное содержимое в момент сида можно посмотреть командой и в самом
`backend/src/db/seed.js` (внизу функция `summary()`).

## 2. Как база выстроена под логику проекта

База спроектирована «от экранов прототипа»: каждая таблица покрывает данные
конкретного экрана (карта связей — в `docs/prototype-connection-map.md`),
а ключевые правила бизнеса реализованы прямо в схеме/коде подключения:

1. **Запись на услугу** (главный сценарий) — `bookings` + `services` + `masters` + `clients`.
   Свободное время **не хранится**, а **вычисляется** на лету из
   `master_schedule` − `bookings` − `work_blocks` − `studio_closures` − `slot_holds` (§7 `db-schema.md`).
   Это исключает рассинхрон «в таблице слотов свободно, а на деле занято».

2. **Шаг «выбрать мастера»** — `master_services`: показываются только мастера,
   умеющие выбранную услугу (как в прототипе: Анна — маникюрные услуги, Ольга — брови).
   Отсюда в сиде ровно те связи «мастер ↔ услуга», которые есть в `MASTERS[].services` прототипа.

3. **Деньги** — только целые копейки (`price_kopecks`, `amount_kopecks`),
   никаких дробных `REAL`. Цена услуги **не дублируется** в записи — берётся JOIN'ом.

4. **Время** — текст ISO `YYYY-MM-DD HH:MM:SS`, локальное (студия в одном городе).
   В записи одна колонка `starts_at` + вычисленный `ends_at`; лексикографическая
   сортировка совпадает с хронологической.

5. **Пароли** — в `users.password_hash` только scrypt-хеш (встроенный
   `crypto.scrypt`, параметры стойкости `N/r/p` и соль хранятся вместе с хешем),
   открытый текст не хранится нигде. Пароль попадает в базу исключительно в виде
   хеша через сид.

6. **Права** — роли хранятся СПИСКОМ в `user_roles` (у человека может быть
   несколько ролей, например `master` + `owner`; колонка `users.role` удалена
   миграцией 007). Проверка «есть ли нужная роль» (а не «равна ли»), роль
   читается из базы на каждый запрос — не из токена и не из запроса.
   `users.master_id` UNIQUE: у каждого мастера не больше одного аккаунта.

7. **Токены входа** — случайный токен выписывается на срок `AUTH_TTL_SECONDS`
   (по умолчанию 7 суток); в БД (`auth_sessions`) хранится только его SHA-256
   плюс `expires_at` и `revoked_at`. Выход отзывает сессию сразу, истёкшие сессии
   чистит фоновая задача. Вход и регистрация лимитированы по частоте.

8. **Защита от пересечения записей** — триггеры `trg_bookings_no_overlap_insert/update`
   (миграции 004–005) отклоняют запись, пересекающую активную запись мастера
   (вплотную — допустимо, отменённые не считаются). Запись с признаком
   `force_override = 1` (ставит только роль `owner`) проходит наложение, но сама
   дальше блокирует других. Транзакции создания/переноса идут на `BEGIN IMMEDIATE`,
   чтобы гонка «оба прочитали слот свободным» заканчивалась ошибкой триггера,
   а не задвоением (±8.5, §8.18 `db-schema.md`).

## 3. Сложности, с которыми столкнулись, и как их решили

### 3.1. Переход с внешнего SQLite-модуля на встроенный `node:sqlite`
**Проблема:** `better-sqlite3` — native-расширение: требует сборки/предкомпилированных
бинарников на каждой машине и на сервере, добавляет хрупкость установке (`npm ci`).

**Решение:** перевели подключение на встроенный модуль Node.js `node:sqlite`
(`DatabaseSync`), внешний пакет удалён из `dependencies`. Правки в `connection.js`:

- нет метода `.pragma()` → все PRAGMA задаются через `db.exec(...)`;
- нет `db.backup()` → консистентная копия через `VACUUM INTO '...'` (`backup.js`);
- для совместимости с прежним API добавлена обёртка `db.transaction(fn)`
  (BEGIN/COMMIT/ROLLBACK), переиспользуется раннером миграций.

### 3.2. Требование к версии Node — сюрприз на сервере (важно!)
**Проблема:** `node:sqlite` без экспериментального флага доступен только с **Node 22.13.0**.
На версиях ниже модуля просто нет (или он требовал `--experimental-sqlite`).

**Решение (зафиксировано в коде и здесь, чтобы это не выяснилось на бекете):**
- `backend/package.json` → `"engines": { "node": ">=22.13" }`;
- `backend/.npmrc` → `engine-strict=true`, чтобы `npm install` на сервере
  останавливался с ошибкой на неподходящей версии Node, а не падал потом в рантайме.

**Что ставить на сервер:** минимум 22.13.0, рекомендуется актуальная LTS-строка 22.
Проверка перед деплоем: `node --version` (должно быть `v22.13.0+`).
Подробнее — в `build_diary.md`, раздел «Backend (Node.js): переход на встроенный SQLite».

### 3.3. Внешние ключи в SQLite не работают «из коробки»
**Проблема:** SQLite по умолчанию игнорирует `REFERENCES` — «бить ограничения» можно
только если явно включить `PRAGMA foreign_keys = ON`. Без этого удалился бы мастер
с записями.

**Решение:** PRAGMA включается **при каждом подключении** в `connection.js`
(не в миграции — иначе правило снова потерялось бы при новом подключении).
Проверено тестом: вставка записи с `master_id = 9999` отклоняется бабой
(`FOREIGN KEY constraint failed`), при выключенном PRAGMA — проходит.

### 3.4. Идемпотентность миграций
**Проблема:** «таблица уже существует» при повторном запуске `CREATE TABLE`.

**Решение:** раннер `runMigrations.js` применяет `.sql`-файлы из `migrations/` по
алфавиту и записывает применённые в `schema_migrations`; повторный запуск их
пропускает. Сброс `db:reset` полностью удаляет файл БД (и `-wal`/`-shm`)
и применяет миграции заново; в production запрещён (`reset.js`).

### 3.5. Идемпотентность сида (дубли при повторном запуске)
**Проблема:** повторный `db:seed` копил бы дубли мастеров, услуг, записей.

**Решение:** `seed.js` перед каждой вставкой проверяет существование (по `name`,
`phone`, `username`, `(master_id, weekday)` и т.д.) — при повторном запуске создаётся 0 строк.
Проверено двумя последовательными запусками (второй дал нули во всех таблицах).

### 3.6. Пароли только хешем
**Проблема:** в базе не должен лежать открытый пароль.

**Решение:** пароли хеширует `hashPassword` (`lib/passwords.js`) встроенным
`crypto.scrypt` — формат самодостаточен `scrypt$N$r$p$salt$hash` (параметры
стойкости и уникальная соль хранятся вместе с хешем; никаких native-модулей,
нужен только `crypto` из Node). Сид хеширует пароли той же функцией; в БД
только `scrypt$16384$8$1$<salt>$<hash>`. Проверено сканированием всех таблиц —
открытых паролей нет.

### 3.7. Локальная машина без Node — верификация Python-эквивалентами
**Проблема:** на dev-машине Node недоступен, `npm run db:*` запустить нельзя.

**Решение:** миграции и сид верифицируются Python-эквивалентами, которые исполняют
**те же `.sql`-файлы** и повторяют логику `seed.js`. Файл базы
`backend/data/nogotki.db` создаётся этими прогонами и является настоящим
SQLite-файлом, который сервер поднимет как есть.

### 3.8. Бэкапы
**Проблема:** node:sqlite не умеет «живое» копирование базы.

**Решение:** `db:backup` делает `VACUUM INTO` (консистентная копия) и хранит
последние 14 копий в `backend/data/backups/`.

### 3.9. Миграция 003 — добавление таблицы в «горящую» базу с данными
**Проблема:** для API понадобилась привязка клиента к аккаунту (`clients.user_id`)
и удержание слотов (`slot_holds`) — а в `backend/data/nogotki.db` уже лежали сид-данные.

**Решение:** обычная миграция с `ALTER TABLE … ADD COLUMN` (nullable — существующие
строки не ломаются) + `CREATE TABLE` для новых сущностей. Верифицирована двумя
прогонами: на **свежей** базе все 3 миграции применяются подряд без ошибок, и на
**копии сид-базы** `ALTER` не падает на заполненной таблице (SQLite позволяет
добавлять nullable-колонку с NULL в существующих строках).

### 3.10. API на машине без Node — статическая проверка вместо запуска
**Проблема:** роуты Express (auth, catalog, holds, bookings, admin) и служебные
модули API собраны, но локально запустить сервер нельзя — Node не установлен.

**Решение:** код проверяется статически (сверка экспортов/импортов, прав доступа,
числа `router.method` против мидлварей), а целостность схемы — Python-эквивалентами
миграций (та же SQL-логика). Реальный запуск — на машине с Node (`npm install`, `npm start`).

### 3.11. Осознанное наложение `force_override` — миграция 005
**Проблема:** администратору нужно записать клиента, даже если расписание мастера
занято (срочный/важный визит), но клиент не должен получить такую возможность.

**Решение:** у `bookings` колонка `force_override` (0/1). Ставит её в `POST /bookings`
только роль `owner` (`hasRole(req.user, 'owner')` в `bookings.js`) — для `client`/`master`
значение в теле запроса просто не читается (игнорируется, без подсказки об ошибке).
Триггеры пересечения и частичный UNIQUE-индекс пропускают записи с признаком;
уже созданная такая запись блокирует других кандидатов как обычная. Снятие признака
с пересекающей записи UPDATE-триггер откатит. Проверено Python-эквивалентами (миграции 1–5).

### 3.12. Единая функция создания записи для всех ролей
**Проблема:** запись в `bookings` может создаваться разными путями (API разных ролей,
сид), что рассинхронизирует поля (`force_override`, `status`) и права.
**Решение:** вставка сведена к одной функции `q.createBooking` (queries.js). Она
используется в `POST /bookings` всеми тремя ролями (`client` — на себя через связку
user→clients; `owner`/`master` — на клиента по `client_id` из тела; `master` ещё обязан
указать свой `master_id`, соответствие `users.master_id`). Признак `force_override`
читается только для `owner`. `seed.js` засевает записи той же `createBooking`
(передаёт `status`), отдельного `INSERT INTO bookings` в коде нет.

### 3.13. Покрытие функций паспорта — публичная информация о студии, расписание мастера и статистика
**Проблема:** при сверке эндпоинтов с функциями паспорта продукта не хватало трёх
групп: «О студии» (адрес/телефон/график), управления расписанием мастера и дашборда
админки.
**Решение:**
- `GET /api/studio` — публичная информация о студии из `studio_info` + сводный график
  работы студии по дням недели (агрегат `master_schedule` активных мастеров, catalog.js).
- `GET/PUT /api/admin/masters/:id/schedule` — чтение и полная замена недельного
  расписания мастера (вариант `replaceMasterSchedule` в `queries.js`, транзакция
  DELETE+INSERT; `v.boundedInt` проверяет диапазоны 0–1439 / 1–1440 и `end > start`).
- `GET/POST /api/admin/masters/:id/work-blocks`, `DELETE /api/admin/work-blocks/:id` —
  перерывы и выходные мастера (`reason`: break/day_off/vacation/sick/other).
- `GET /api/admin/stats` — дашборд (`statsDashboard`): всего записей, активных,
  сумма активных в копейках (цена услуги) и число мастеров.

Свободные слоты мастера учитывают эти блокировки и расписание автоматически
(`getBusyIntervals` в `queries.js` читает `master_schedule`, `work_blocks`,
`studio_closures`, `slot_holds` и записи).

### 3.15. Безопасность аутентификации — миграция 007
**Проблема:** требования безопасности: пароли на медленном хеше без native-модулей,
токены с ограниченным сроком и хешем в БД, роли списком из базы, проверка «своё ли
объекта», rate limit, никаких внутренностей в ошибках.

**Решение (миграция `007_auth_security.sql` + код):**
- **Пароли** — `lib/passwords.js`: `crypto.scrypt` (встроенный, без bcrypt/argon2 —
  native-модули не соберутся на боевом сервере); соль и `N/r/p` хранятся в самом
  хеше; `timingSafeEqual` при проверке; то же для сида.
- **Токены** — случайный (`randomBytes(32)`), в БД (`auth_sessions`) только
  `SHA-256` + `expires_at` (TTL из `AUTH_TTL_SECONDS`) + `revoked_at`. Выход
  отзывает сессию немедленно; истёкшие/отозванные чистит фоновая задача.
  `AUTH_SECRET` больше не нужен (токены не подписываются).
- **Роли** — `user_roles` (список; колонка `users.role` пересозданием удалена).
  `requireRole`/проверки в роутах используют `hasRole(user, role)` — «есть ли
  роль», а не «равна ли». Роль читается из базы на каждый запрос
  (`middleware/auth.js`), из токена/запроса не берётся.
- **Проверки на каждом эндпоинте** — вход (`authRequired`), роль
  (`requireRole(...)`), «его ли объект» (`checkAccess`): клиент — свои записи,
  мастер — записи своего `master_id`, owner — все.
- **Валидация входов** — типы/форматы/длины через `lib/validate.js`; новое:
  «время не в прошлом» (`assertNotPast` в `lib/time.js`) для создания записи,
  удержания и переноса (bookings/holds) и блокировок мастера (admin); поля,
  которые пользователь не имеет права задавать сам (например `force_override`
  для client/master, `role` при регистрации), отбрасываются.
- **Rate limit** — `middleware/rateLimit.js` на `POST /auth/login` и
  `POST /auth/register` (окно 60 с, 5 попыток по IP; дополнительно узел по
  логину против перебора аккаунта с разных IP; ответ 429).
- **Параметризация** — все запросы через подготовленные выражения; интерполяции
  только литералами (имена таблиц/колонок), пользовательские значения — только
  через параметры `?`.
- **Секреты** — в коде нет ключей; единственный источник — `.env` (в репозитории
  только `.env.example`). Настройки, которые меняет владелец (услуги, мастера,
  расписание, отзывы), — уже в базе, а не в `.env`.
- **Ошибки** — 5xx наружу только «Внутренняя ошибка сервера.» без текстов БД,
  путей, стеков; 4xx — сообщения валидаторов (`app.js`).

Проверено: автотест сценариев (см. §4) — роли списком, `user_roles`,
`auth_sessions`, отзыв сессии; обновление существующей базы 001–006 → 007
переносит роли в `user_roles` без потерь.

### 3.14. Обратная связь клиентов — миграция 006
**Проблема:** в паспорте продукта есть функция «Обратная связь и отзывы» (клиент
оставляет отзыв/жалобу после посещения), а эндпоинтов и таблицы не было.
**Решение:** миграция `006_client_feedback.sql` создаёт таблицу `client_feedback`
(text 1–2000, status: new/read/answered, FK → clients). Эндпоинты:
- `POST /api/feedback` — роль `client` оставляет отзыв;
- `GET /api/feedback` — свои отзывы клиента (или все для owner);
- `GET /api/admin/feedback?status=` и `PATCH /api/admin/feedback/:id` — владелец
  просматривает обращения и меняет статус (`requireRole('owner')`).

## 5. Правило ведения этого документа

1. **Документ ведём последовательно вместе с проектом:** каждое дополнение
   (новая таблица/поле/миграция, изменение ролей, новый сид, новый PRAGMA,
   решение по инфраструктуре) сначала обновляет `docs/db-schema.md`
   (если это схема), а **этот файл** — разделы «Текущее состояние» и/или
   «Сложности», если изменилась фактическая структура или добавился урок.
2. **Созависимость:** миграция → `db-schema.md` → `database.md` → `seed.js`
   (если нужны тестовые данные) → повторная верификация (сид/миграции).
3. **Изменения версии Node или способа подключения** (новый драйвер, PRAGMA,
   движок БД) фиксировать в §3 с обязательной пометкой «важно для деплоя».
4. Этот файл должен оставаться **читаемым агентам проекта**: короткие абзацы,
   таблицы, ссылки на код/файлы, без вымышленных деталей.
