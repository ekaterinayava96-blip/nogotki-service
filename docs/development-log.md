## 1. Что было сломано

Две ошибки, обе найдены при ручной проверке сервиса.

### 1.1 Резервное копирование базы не запускалось

Копий базы не существовало ни одной: папка `backend/data/backups` была пуста.
Команда `node src/db/backup.js` при этом работала и копию создавала.

### 1.2 Проверки прав доступа в HTTP-слое отсутствовали

Правила доступа проверяются вручную на каждом маршруте, механизма «запрещено по
умолчанию» нет. Утечки при этом не было — 46 маршрутов × три роли проверены,
ни один не отдал данные кому не следует. Опасность была в другом: забытый
`requireRole` ничем не был бы замечен.

### 1.3 Регрессия, которую внёс мой же набор проверки

Сразу после исправления 1.2 пользователь обнаружил, что из клиентского выбора
пропала мастер Екатерина. Так же ушла услуга «Маникюр с покрытием гель-лаком».

---

## 2. Причины

| Ошибка | Причина |
|---|---|
| **Нет копий базы** | Копирование вызывалось только при `require.main === module` — исключительно при ручном запуске скрипта. При старте сервера условие ложно, и не вызывал его никто: ни обработчик, ни таймер. Само копирование в коде невозможно — для этого нужен планировщик ОС, а он был описан лишь комментарием с готовой строкой cron. Программа исправна, обязательного шага нет, а проверить нечем: команда запускается и работает |
| **Нет проверок прав** | Имеющийся набор `test_role_scenarios.py` проверяет **копию правил**, а не настоящий код: функция `api_create_bookings()` заново описывает права доступа на Python и ходит в базу мимо Express. Забытый `requireRole` такой набор не заметит — он проверяет сам себя |
| **Пропал мастер** | Мой набор дёргал **все** маршруты, включая изменяющие, сессией владельца. `DELETE /api/admin/masters/:id` при наличии записей у мастера не удаляет строку, а молча деактивирует: `UPDATE masters SET is_active = 0`, `outcome: "disabled"`. У Екатерины записи были — значит `DELETE` вернул `200`. Так же ушла услуга: `DELETE /api/admin/services/:id` устроен так же. Отметка времени у обеих записей совпала — один прогон |

**Почему набор при этом показывал «успех».** Он проверял, что маршрут не отдаст
2xx анониму и не пустит клиента, а владельцу — что тот не получит 5xx. Мягкое
удаление возвращает 200. Для проверки прав это успех, для данных — потеря. Тест
был не бесполезен, а вреден.

## 3. Как исправлено

### 1.1 Бэкапы — коммит `96e499c`

- Расписание перенесено внутрь приложения: `startBackupSchedule()` в
  `backend/src/db/backup.js`, запуск в `src/index.js` рядом с чисткой удержаний.
- Планировщик ОС больше не нужен. Таймер помечен `unref()`, сбой копирования
  перехватывается и пишется в журнал — теряется копия, а не работающий сайт.
- Настройки `BACKUP_INTERVAL_HOURS` (по умолчанию 24, `0` отключает),
  `BACKUP_KEEP` (14), `BACKUP_ON_START` проверяются на старте: мусор в `.env`
  останавливает сервер, а не тихо отключает страховку.
- Проверено: при интервале 18 секунд снято 7 копий подряд без ручного запуска;
  копия проходит `integrity_check` и совпадает с рабочей базой; `VACUUM INTO` не
  мешает записи — 6 записей созданы, пока копирование шло.

### 1.2 Проверки прав — коммиты `79ec909` и `9233257`

- Добавлен `backend/tests/test_access_matrix.py`: маршруты собираются прямо из
  исходников `backend/src/routes/*.js`, поэтому новый маршрут попадает в
  проверку сам. Каждый дёргается анонимом, клиентом и владельцем.
- Набор проверен на сломанном коде: с проверки снят `authRequired` — поймано
  (`ok=120 fail=1`).
- Исправлена вредность самого набора: владельцу уходят только `GET` и `HEAD`,
  25 изменяющих маршрутов пропускаются. Аноним и клиент по-прежнему дёргаются
  всеми методами — их запросы отклоняются до обработчика и безвредны.
- Проверка «ничего не сломал»: снимок состояния до и после прогона — мастера,
  услуги, связи, расписание, блокировки, счётчики, данные студии. Прогон не
  меняет ничего.

### 1.3 Пропавший мастер

- Екатерина и услуга № 1 возвращены, свободные окна мастера работают.
- Поведение `DELETE` вынесено отдельной находкой 1.3 в `docs/test-checklist.md`.

## 4. Косметические недочёты, которые остались

Не мешают работе, править можно в любую очередь.

| № | Находка | Суть |
|---|---|---|
| 3.1 | `can_force` приходит числом | Ответ `409` отдаёт `"can_force": 1` вместо `true`. Для JavaScript проверка `=== true` не сработает; работает проверка истинности |
| 3.2 | Отказ без кода ошибки | `POST /api/bookings/:id/cancel` при чужой записи отдаёт `403` без `error.code`, тогда как остальные ответы код имеют. На безопасность не влияет |
| 3.3 | Неиспользуемая таблица `payments` | Объявлена в схеме с провайдерами (`yookassa`, `sbp`, `cash`) и статусами. Строк ноль, обращений в коде ноль. Противоречит заявленному «онлайн-оплаты нет» и сбивает с толку читателя схемы. Отдельно: у неё `ON DELETE RESTRICT` на запись — при включении оплаты записи с платежами станет нельзя удалять |

Побочно замечено, но в отдельный список не вынесено: сообщение о конфликте слота
заканчивается двоеточием, когда свободных вариантов нет
(`Это время уже занято. Возьмите один из свободных вариантов:` — и пусто).
Воспроизводится, когда в ближайшую неделю свободных окон не осталось вовсе.

## 5. Что осталось не исправленным

Из первой группы — две находки, из второй — все семь.

| № | Находка | Почему не исправлено |
|---|---|---|
| 1.3 | `DELETE` у мастера и услуги молча деактивирует их | Одинаково выглядящий вызов с двумя последствиями: отключает при записях, удаляет насовсем без них, оба раза отвечает `200`. Развести методы или оставить и закрыть предупреждением — решение продуктовое |
| 1.4 | Защита от двойной записи держится на строковом сравнении дат | `starts_at` и `ends_at` хранятся текстом, триггеры сравнивают их как строки. При записи в формате ISO с `T` и `Z` пересечение проходит. Сейчас весь код пишет через один преобразователь, поэтому живых дыр нет — стрельнёт при первом же новом пути записи (импорт, миграция, ручной SQL). Перевод дат — миграция данных на живой базе |
| 2.1 | Аккаунт внешнего входа не может записаться | `403 NO_CLIENT_PROFILE`: у аккаунта нет строки в `clients`, а она нужна для записи. Яндекс телефон не отдаёт, а `clients.phone` обязателен. Нужно спросить телефон при первом входе или сделать поле необязательным |
| 2.2 | Гость на `/admin.html` получает отказ вместо входа | Вместо перехода на страницу входа отдаётся `403` со страницей «Доступ закрыт», где предложения войти нет. Правка локальная — одна проверка в `requireOwnerPage` |
| 2.3 | Сброс пароля не подключён | `501 PASSWORD_RESET_UNAVAILABLE`. Почтового провайдера в проекте нет. Подменять заглушкой нельзя — это обещание, что письмо дойдёт |
| 2.4 | Текст при отмене врёт о последствиях | Две ветки окна обещают «занятое время уже не вернуть в расписание», хотя слот освобождается — проверено. Отговаривает отменять понапрасну |
| 2.5 | Из панели нельзя создать запись поверх занятого | Две причины одна: слоты отдаются только свободные, а эндпоинта списка клиентов нет — `/api/clients` и `/api/admin/clients` отдают `404` даже под админом |
| 2.6 | Регистрация не по электронной почте | Форма собирает логин, пароль, имя и телефон. Если почта действительно нужна — блокер запуска |
| 2.7 | База забита тестовыми данными | 165 пользователей, 161 клиент, 178 записей, 13 отключённых услуг. Слоты расходуются, списки в панели забиты. Источник части мусора найден: тесты отключали реальные сущности через `DELETE` |

### Общие причины, которые снимают сразу несколько пунктов

| Причина | Что из неё следует |
|---|---|
| Нет почтового провайдера | 2.3 и ограничение «уведомления только в кабинете» |
| Внешний вход создаёт аккаунт без профиля клиента | 2.1 |
| Нет списка клиентов + слоты только свободные | 2.5 |
| Проверки шли по рабочей базе без уборки | 2.7 |

## 6. Границы проверок

Не покрыто: инъекции в параметры SQL, исчерпание лимитов запросов, массовое
присваивание полей на остальных эндпоинтах, нагрузка при большом числе
одновременных записей. Права на конкретную чужую строку проверяет
`test_role_scenarios.py`, набор по матрице смотрит на код ответа, а не на
содержимое.
