## 1. Что было сломано

Две ошибки, обе найдены при ручной проверке сервиса.

### 1.1 Резервное копирование базы не запускалось

Копий базы не существовало ни одной: папка `backend/data/backups` была пуста.
Команда `node src/db/backup.js` при этом работала и копию создавала.

### 1.2 Проверки прав доступа в HTTP-слое отсутствовали

Правила доступа проверяются вручную на каждом маршруте, механизма «запрещено по
умолчанию» нет. Утечки при этом не было — 46 маршрутов × три роли проверены,
ни один не отдал данные кому не следует. Опасность была в другом: забытый
`requireRole` ничем не был бы замечен.

### 1.3 Регрессия, которую внёс мой же набор проверки

Сразу после исправления 1.2 пользователь обнаружил, что из клиентского выбора
пропала мастер Екатерина. Так же ушла услуга «Маникюр с покрытием гель-лаком».

## 2. Причины

| Ошибка | Причина |
|---|---|
| **Нет копий базы** | Копирование вызывалось только при `require.main === module` — исключительно при ручном запуске скрипта. При старте сервера условие ложно, и не вызывал его никто: ни обработчик, ни таймер. Само копирование в коде невозможно — для этого нужен планировщик ОС, а он был описан лишь комментарием с готовой строкой cron. Программа исправна, обязательного шага нет, а проверить нечем: команда запускается и работает |
| **Нет проверок прав** | Имеющийся набор `test_role_scenarios.py` проверяет **копию правил**, а не настоящий код: функция `api_create_bookings()` заново описывает права доступа на Python и ходит в базу мимо Express. Забытый `requireRole` такой набор не заметит — он проверяет сам себя |
| **Пропал мастер** | Мой набор дёргал **все** маршруты, включая изменяющие, сессией владельца. `DELETE /api/admin/masters/:id` при наличии записей у мастера не удаляет строку, а молча деактивирует: `UPDATE masters SET is_active = 0`, `outcome: "disabled"`. У Екатерины записи были — значит `DELETE` вернул `200`. Так же ушла услуга: `DELETE /api/admin/services/:id` устроен так же. Отметка времени у обеих записей совпала — один прогон |

**Почему набор при этом показывал «успех».** Он проверял, что маршрут не отдаст
2xx анониму и не пустит клиента, а владельцу — что тот не получит 5xx. Мягкое
удаление возвращает 200. Для проверки прав это успех, для данных — потеря. Тест
был не бесполезен, а вреден.

## 3. Как исправлено

### 1.1 Бэкапы — коммит `96e499c`

- Расписание перенесено внутрь приложения: `startBackupSchedule()` в
  `backend/src/db/backup.js`, запуск в `src/index.js` рядом с чисткой удержаний.
- Планировщик ОС больше не нужен. Таймер помечен `unref()`, сбой копирования
  перехватывается и пишется в журнал — теряется копия, а не работающий сайт.
- Настройки `BACKUP_INTERVAL_HOURS` (по умолчанию 24, `0` отключает),
  `BACKUP_KEEP` (14), `BACKUP_ON_START` проверяются на старте: мусор в `.env`
  останавливает сервер, а не тихо отключает страховку.
- Проверено: при интервале 18 секунд снято 7 копий подряд без ручного запуска;
  копия проходит `integrity_check` и совпадает с рабочей базой; `VACUUM INTO` не
  мешает записи — 6 записей созданы, пока копирование шло.

### 1.2 Проверки прав — коммиты `79ec909` и `9233257`

- Добавлен `backend/tests/test_access_matrix.py`: маршруты собираются прямо из
  исходников `backend/src/routes/*.js`, поэтому новый маршрут попадает в
  проверку сам. Каждый дёргается анонимом, клиентом и владельцем.
- Набор проверен на сломанном коде: с проверки снят `authRequired` — поймано
  (`ok=120 fail=1`).
- Исправлена вредность самого набора: владельцу уходят только `GET` и `HEAD`,
  25 изменяющих маршрутов пропускаются. Аноним и клиент по-прежнему дёргаются
  всеми методами — их запросы отклоняются до обработчика и безвредны.
- Проверка «ничего не сломал»: снимок состояния до и после прогона — мастера,
  услуги, связи, расписание, блокировки, счётчики, данные студии. Прогон не
  меняет ничего.

### 1.3 Пропавший мастер

## 5. Что осталось не исправленным

Из первой группы — две находки, из второй — все семь.

| № | Находка | Почему не исправлено |
|---|---|---|
| 1.3 | `DELETE` у мастера и услуги молча деактивирует их | Одинаково выглядящий вызов с двумя последствиями: отключает при записях, удаляет насовсем без них, оба раза отвечает `200`. Развести методы или оставить и закрыть предупреждением — решение продуктовое |
| 1.4 | Защита от двойной записи держится на строковом сравнении дат | `starts_at` и `ends_at` хранятся текстом, триггеры сравнивают их как строки. При записи в формате ISO с `T` и `Z` пересечение проходит. Сейчас весь код пишет через один преобразователь, поэтому живых дыр нет — стрельнёт при первом же новом пути записи (импорт, миграция, ручной SQL). Перевод дат — миграция данных на живой базе |
| 2.1 | Аккаунт внешнего входа не может записаться | `403 NO_CLIENT_PROFILE`: у аккаунта нет строки в `clients`, а она нужна для записи. Яндекс телефон не отдаёт, а `clients.phone` обязателен. Нужно спросить телефон при первом входе или сделать поле необязательным |
| 2.2 | Гость на `/admin.html` получает отказ вместо входа | Вместо перехода на страницу входа отдаётся `403` со страницей «Доступ закрыт», где предложения войти нет. Правка локальная — одна проверка в `requireOwnerPage` |
| 2.3 | Сброс пароля не подключён | `501 PASSWORD_RESET_UNAVAILABLE`. Почтового провайдера в проекте нет. Подменять заглушкой нельзя — это обещание, что письмо дойдёт |
| 2.4 | Текст при отмене врёт о последствиях | Две ветки окна обещают «занятое время уже не вернуть в расписание», хотя слот освобождается — проверено. Отговаривает отменять понапрасну |
| 2.5 | Из панели нельзя создать запись поверх занятого | Две причины одна: слоты отдаются только свободные, а эндпоинта списка клиентов нет — `/api/clients` и `/api/admin/clients` отдают `404` даже под админом |
| 2.6 | Регистрация не по электронной почте | Форма собирает логин, пароль, имя и телефон. Если почта действительно нужна — блокер запуска |
| 2.7 | База забита тестовыми данными | 165 пользователей, 161 клиент, 178 записей, 13 отключённых услуг. Слоты расходуются, списки в панели забиты. Источник части мусора найден: тесты отключали реальные сущности через `DELETE` |

  (`deploy/nginx.conf`).
- **Оплата:** регистрация оплачена до 20.10.2026.
- **Идентификация администратора через Госуслуги:** подтверждена.
- **DNS уже настроен:** A → `92.53.96.201`, AAAA → `2a03:6f00:1::5c35:60c9`,
  MX → `mx1/mx2.timeweb.ru`, SPF включён, NS — четыре сервера Timeweb.

**Решение по данным:** сервис работает на вымышленных и моих собственных данных,
чужие настоящие данные в него не заводим, реальных клиентов не приглашаем.

### 7.2 Оплачен хостинг, но тариф не подходит под приложение

Куплен виртуальный хостинг Timeweb, тариф 452 ₽/мес: 2 сайта, 15 ГБ диска,
2 базы данных, 100 «CP», FTP без лимита. FTP-доступ `cn087832` на
`vh460.timeweb.ru` проверен, вход работает.

**Почему не подходит.** Это виртуальный хостинг, а не VPS: в корне только
`public_html`, внутри — `cgi-bin` и `index.htm` с заглушкой Timeweb. На таком
хостинге нет долгоживущего процесса, который слушал бы порт.

Приложению нужно то, чего здесь нет:

| Требуется проектом | Есть на хостинге |
|---|---|
| Node.js `>=22.13` (встроенный `node:sqlite`) | нет, только PHP и CGI |
| Постоянный процесс Express на порту 3000 | нет, только `public_html` |
| systemd-юнит и `curl` для управления | нет доступа, SSH отклоняется: `Permission denied (publickey,password)` |
| Свой диск под SQLite-базу | 15 ГБ на 2 сайта, общий |

«2 базы данных» из тарифа — это MySQL, а проекту нужна SQLite файлом
(`node:sqlite`). Перенос на MySQL означал бы переписывать слой доступа к данным.

**Что отдаёт домен сейчас.** `http://nogti.com.ru/` отвечает `200`, но это
заглушка Timeweb «Сайт не определён», а не приложение. По `https://` соединение
падает с ошибкой SSL/TLS — сертификата нет.

**Решение:** заказать VPS. Домен переносить не нужно — меняется один IP в
A-записи. Порядок развёртывания и параметры сервера описаны в `docs/deploy.md`.

## 8. Подготовка к запуску в контейнере — 2026-10-12

Сервер собирает образ заново при каждом обновлении, и всё содержимое контейнера
при этом стирается. Единственное, что переживает пересборку, — том,
подключённый снаружи. Под это и приведено приложение.

### 8.1 Где лежит база

Файл базы локально остался на прежнем месте, `backend/data/nogotki.db`: рядом с
ним нет файлов кода, отдельная папка была и раньше. Переносить его на диск
пользователя смысла не было. Изменилось другое — **путь к базе перестал быть
частью кода и стал настройкой**:

```js
// backend/src/config.js:116
dbPath: path.resolve(__dirname, '..', process.env.DB_PATH || 'data/nogotki.db'),
```

Значение по умолчанию (`data/nogotki.db`, то есть рядом с кодом) нужно для
локального запуска, а в образе путь переопределён на `/data/nogotki.db` —
каталог, который подключается к контейнеру томом и потому переживает
пересборку. Папку создавать вручную не нужно: `backend/src/db/connection.js:10`
вызывает `fs.mkdirSync(..., { recursive: true })` при первом обращении к базе,
поэтому первый запуск на чистом сервере падать не будет.

Резервные копии базы кладутся рядом с ней же, в `<каталог базы>/backups/`
(`backend/src/db/backup.js`), и переезжают вместе с томом — отдельно настраивать
ничего не нужно.

### 8.2 Миграции применяются самостоятельно

Отдельную команду на сервере набирать не придётся. При каждом старте приложение
само проверяет настройки, создаёт базу, применяет миграции из
`backend/src/db/migrations/*.sql` и только потом открывает порт.

Здесь была найдена и исправлена настоящая ошибка порядка: `app.listen()`
вызывался **до** `boot()`, поэтому сервер успевал начать принимать запросы к
схеме, которой могло ещё не быть. Теперь в `backend/src/index.js` сначала
вызывается `boot()`, затем `app.listen()`, а корректная остановка по SIGTERM
перенесена в отдельную функцию `attachServer(server)` из `backend/src/startup.js`.

Повторно уже применённые миграции не выполняются: имена файлов пишутся в
таблицу `schema_migrations`, при следующем старте они печатаются как `skip`.
Проверено на чистой базе в режиме `production`: первый запуск — `apply 001…012`,
второй — `skip 001…012`.

### 8.3 Что не попадает в образ

Добавлен `.dockerignore` в корень репозитория. Локальная тестовая база в образ
не попадает — и это главная причина, по которой файл нужен: иначе она затрёт
настоящую базу на сервере. Исключены `node_modules` (ставится при сборке),
`.env` и `.env.*` (секреты задаются на сервере), `.git`, кэши и `docs` с
`prototype`.

Отдельная тонкость: правила `.dockerignore` сопоставляются с путём целиком, и
шаблон без `/` срабатывает только в корне контекста. Поэтому строка `*.db`
сама по себе не закрыла бы `backend/data/nogotki.db` — базу закрывает строка
`backend/data`, исключающая папку целиком. Обе строки оставлены намеренно.

### 8.5 Настройки, которые надо задать на сервере

**Обязательные:**

| Настройка | Значение | Почему |
|---|---|---|
| `DB_PATH` | `/data/nogotki.db` | При `NODE_ENV=production` без неё приложение отказывается стартовать (проверка в `src/config.js`) |
| Том с базой | `docker volume create nogotki-data` | Не переменная, но без него база пропадёт вместе с контейнером. Имя постоянное: новый том означает пустую базу |
| `SEED_ADMIN_PASSWORD` | пароль владельца | Нужен один раз при первом заполнении базы (`npm run db:seed`) |
| `SEED_MASTER_PASSWORD` | пароль мастера | То же, и он должен отличаться от пароля владельца |
| `SEED_CLIENT_PASSWORD` | пароль клиента | То же, третий разных пароля |

**С разумным значением по умолчанию — задавать необязательно:**

| Настройка | По умолчанию | Когда менять |
|---|---|---|
| `PORT` | `3000` | Если наружу отдаётся другой порт |
| `NODE_ENV` | `production` в образе | Следить, чтобы не переопределили на `development` |
| `TRUST_PROXY` | `1` | Только `0`, если контейнер выставлен в интернет напрямую, без nginx: иначе ограничение попыток входа видит адрес прокси, а не клиента |
| `AUTH_TTL_SECONDS` | `604800` (7 суток) | — |
| `BACKUP_INTERVAL_HOURS` | `24` | `0` отключает копирование совсем |
| `BACKUP_KEEP` | `14` | — |
| `BACKUP_ON_START` | `0` | Для контейнера разумно `1`: копия снимается сразу при старте |
| `YANDEX_STUB` | выключена | Держать выключенной: заглушка пускает в аккаунт без проверки у Яндекса |
| `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI` | пусто | Только если нужен настоящий внешний вход |
