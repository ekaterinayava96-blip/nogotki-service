# Чек-лист находок после проверки сервиса

> **Важно о происхождении этого списка.** Файл `docs/test-checklist.md` в репозитории
> отсутствовал — при поиске не найден ни сам файл, ни упоминания него в истории.
> Поэтому список ниже собран заново из находок, которые действительно были
> проверены и подтверждены в ходе работы над сервисом. Если подразумевался другой
> перечень — пришлите его, и я пересоберу разбивку.

Проверено: API, страницы в браузере на ширине 390px, схема базы, поведение при
прямом SQL-обходе проверок. Дата проверки — 2026-10-05.

## Группа 1. Проблемы, которые портят данные или открывают чужую информацию

Подтверждённых утечек чужих данных **нет** — попытки достать чужую запись
делались 11 способами, все отклонены. Ниже то, что приводит к таким последствиям
либо к потере данных.

### 1.1 Резервное копирование не запускается автоматически

**Статус: ИСПРАВЛЕНО** (проверено 2026-10-07; правка — отдельный коммит в `main`)

**Что было не так.** `npm run db:backup` существовал (`backend/src/db/backup.js`),
делал копию и хранил 14 последних, но сам не запускался. Планировщик ОС был описан
лишь в комментарии и на сервере не настроен — копий не существовало вовсе.

**Причина.** Копирование вызывалось только при `require.main === module`, то есть
исключительно при ручном запуске скрипта. Больше его не вызывал никто: ни один
обработчик, ни один таймер в приложении. Приложение и не умеет само планировать
события — для этого нужен планировщик ОС, а он не был настроен. Получилось
недоделанное внедрение: код написан и исправен, обязательного шага нет.

**Что сделано.** Расписание перенесено внутрь приложения — планировщик ОС больше
не нужен. Таймер поднимается в `src/index.js` рядом с чисткой удержаний,
по настройкам `BACKUP_INTERVAL_HOURS` (по умолчанию 24, `0` отключает),
`BACKUP_KEEP` (14) и `BACKUP_ON_START` (копия сразу при старке). Ручной запуск
сохранён — он нужен перед переездом.

**Новый результат проверки.** Копии снимаются сами, без участия человека:

| Проверка | Результат |
|---|---|
| Копия появляется без ручного запуска | Да: при интервале 18 секунд снято 7 копий подряд, ни одну не запускал вручную |
| Копия пригодна к восстановлению | `integrity_check` = `ok`, 7 таблиц совпадают с рабочей базой, 39 индексов на месте |
| Ручной запуск `node src/db/backup.js` | По-прежнему работает |
| Ретеншн | 17 копий → осталось 14, остались самые свежие |
| Отключение `BACKUP_INTERVAL_HOURS=0` | Копий нет, сервер работает |
| Мусор в настройках (`abc`, `-5`, `KEEP=0`) | Отвергается на старте с внятной ошибкой |
| Влияние на работу сервиса | Нет: 6 записей создано и 6 проверок `/api/auth/me` прошли, пока шёл `VACUUM INTO` |

**Что осталось на усмотрение.** Копия лежит на том же диске, что и база, поэтому
при смерти диска не спасёт — это в разделе про вывозить копии наружу.

### 1.2 Права доступа проверяются вручную на каждом маршруте

**Статус: ИСПРАВЛЕНО** (проверено 2026-10-07; правка — отдельный коммит в `main`)

**Что было не так.** Единого «запрещено по умолчанию» механизма нет: каждый
маршрут сам решает, как проверять роль и владельца. Сейчас написано правильно
везде, где есть, но стоит забыть один новый маршрут — и он отдаст чужие данные
без предупреждения.

**Что выяснилось при разборе.** Главная опасность нашла объяснение. Набор
`test_role_scenarios.py`, который проверяет роли, **не проверяет HTTP-слой**:
функция `api_create_bookings()` заново описывает правила доступа на Python. То
есть набор проверяет копию логики, а не настоящие middleware Express. Если в
маршруте забыть `requireRole`, этот набор останется зелёным — он ничего не
заметит. Проверки прав в HTTP-слое у проекта не было вовсе.

**Что сделано.** Добавлен `backend/tests/test_access_matrix.py`: собирает
маршруты прямо из исходников `backend/src/routes/*.js` и дёргает каждый тремя
ролями — аноним, клиент, владелец. Правило простое: маршрут, не помеченный
публичным, не должен отвечать 2xx ни анониму, ни чужой роли. Сейчас 121
проверка, ноль падений.

Код приложения не менялся — только добавлен тест. Подробности и границы
покрытия — в `docs/frontend-log.md`, раздел 15.

### 1.3 DELETE у мастера и услуги молча деактивирует их

**Статус: найдено, не исправлено**

**Что не так.** `DELETE /api/admin/masters/:id` и `DELETE /api/admin/services/:id`
делают одно и то же по-разному: при наличии записей строка не удаляется, а
деактивируется (`is_active = 0`, `outcome: "disabled"`), без записей — удаляется
насовсем (`outcome: "deleted"`). Оба случая возвращают 200.

**Почему это ловушка.** Одинаково выглядящий вызов с двумя последствиями, о которых
нужно знать заранее. На этом попался мой же набор проверки прав: прогон отключил
мастера Екатерину и услугу «Маникюр с покрытием гель-лаком», и они пропали из
клиентского выбора. Разбор — в `docs/frontend-log.md`, раздел 15.6.

**Что предлагать.** Либо развести методы (`DELETE` всегда удаляет, отключение —
отдельным `PATCH` с `is_active: 0`, как это уже сделано для услуг), либо оставить
как есть и закрыть предупреждением в панели. Решение продуктовое.
### 1.4 Защита от двойной записи держится на строковом сравнении дат

**Что не так.** `bookings.starts_at` и `ends_at` — текст в формате
`ГГГГ-ММ-ДД ЧЧ:ММ:СС`. Триггеры запрета пересечения сравнивают их как строки.
Проверено: если вставить дату в формате ISO с `T` и `Z` (`2026-10-06T09:30:00.000Z`),
пересечение **проходит** — потому что `' '` меньше `'T'`. Все три вида наложения
(точное совпадение, накрытие чужой записи, заезд хвостом на чужую) блокируются
только пока формат записи одинаковый.

**Почему третьим, а не первым.** Дыра не выстреливает сама: сейчас весь код пишет
через один и тот же преобразователь, поэтому пересечения ловятся верно. Она
стрельнёт при первом же новом пути записи — импорте, ручном SQL из бэкапа, миграции.
Дешевле закрыть заранее, чем потом искать, откуда взялись две записи на одно время.

## Группа 2. Проблемы, которые мешают пользоваться

### 2.1 Аккаунт, созданный через внешний вход, не может записаться

**Что не так.** При попытке создать запись — `403 NO_CLIENT_PROFILE`. У аккаунта нет
строки в таблице клиентов, а она нужна для записи. Причина структурная: Яндекс не
отдаёт телефон, а поле `clients.phone` обязательно.

**Почему первым в группе.** Это единственная находка, которая полностью отключает
главное действие сервиса для целого класса пользователей. Человек вошёл, потратил
время на выбор услуги — и упёрся в стену.

### 2.2 Гость на `/admin.html` получает отказ вместо перехода на страницу входа

**Что не так.** Вместо перехода на вход отдаётся `403` со страницей «Доступ закрыт»
и ссылками на главную и записи. Человек, который вышел из аккаунта и хочет вернуться
в панель, упирается в тупик: предложения войти на странице нет.

**Почему вторым.** Ломает естественный путь «вошёл → панель → вышел → снова панель».
Правка маленькая и локальная — одна проверка в `requireOwnerPage`.

### 2.3 Сброс пароля не подключён

**Что не так.** `POST /api/auth/password/forgot` для аккаунта с паролем отвечает
`501 PASSWORD_RESET_UNAVAILABLE`. Письма сервис не отправляет: почтового провайдера
в проекте нет.

**Почему третьим.** Человек с паролем, который его забыл, не может вернуться в
сервис вообще. Это потеря доступа, а не неудобство.

### 2.4 Текст при отмене врёт о последствиях

**Что не так.** В окне отмены две ветки обещают: «занятое время уже не вернуть в
расписание мастера». По факту слот освобождается — проверено: после отмены записи
время снова появилось в списке свободных, и его занял другой клиент. Правильный текст
есть только в ветке бесплатной отмены («Слот освободится для других клиентов»).

**Почему четвёртым.** Ничего не ломает, но отговаривает отменять понапрасну: человек
читает «время не вернуть» и решает не отменять. Для студии это отменённые визиты.

### 2.5 Из панели нельзя создать запись поверх занятого времени

**Что не так.** Две причины одна: форма переноса наполняется `GET
/api/masters/:id/slots`, а он отдаёт только свободные окна — выбрать занятое время
нельзя. А кнопка «Записать клиента на это время» требует выбрать клиента, и
эндпоинта списка клиентов нет: `/api/clients` и `/api/admin/clients` отдают `404`
даже под админом.

**Почему пятым.** Сценарий «администратор кладёт визит поверх чужого» с интерфейса
недостижим, хотя на уровне API он работает и протестирован.

### 2.6 Регистрация не по электронной почте

**Что не так.** В заявленном сценарии клиент «регистрируется по email», а форма
собирает логин, пароль, имя и телефон. Слово `email` не встречается ни в одном
веб-файле проекта. Поле `users.email` появилось только под внешний вход и
заполняется лишь там.

**Почему шестым.** Расхождение с заявленным онбордингом. Если почта действительно
нужна — это блокер запуска; если нет — находку можно закрыть правкой описания.

### 2.7 База забита тестовыми данными

**Что не так.** 59 тестовых клиентов, 128 записей (из них 48 созданы прогонами
проверок), 13 отключённых услуг с именами «Снимок цены», «Услуга А», «Услуга Б».
Пользователей выросло со 88 до 147.

**Почему седьмым.** Слоты расходуются — из-за этого приходится искать день подальше,
чтобы найти свободное окно. В панели списки забиты мусором, и это же мешает
проверять сервис вручную.

## Группа 3. Косметические недочёты

### 3.1 Флаг `can_force` приходит числом, а не `true`

Ответ `409` отдаёт `"can_force": 1`. Для потребителя на JavaScript это скорее
ловушка: проверка `=== true` не сработает. Работает, если проверять истинность.

### 3.2 Отказ в отмене чужой записи идёт без кода ошибки

`POST /api/bookings/:id/cancel` при чужой записи возвращает `403`, но без
`error.code`, тогда как остальные ответы код имеют. На безопасность не влияет,
формально непоследовательно.

### 3.3 Таблица `payments` объявлена, но не используется

В схеме есть таблица `payments` с платёжными провайдерами (`yookassa`, `sbp`,
`cash`) и статусами. Строк в ней ноль, обращений к ней в коде тоже ноль. Противоречит
заявленному ограничению «онлайн-оплаты нет» и сбивает с толку того, кто будет читать
схему. Отдельно отмечу: у неё `ON DELETE RESTRICT` на запись — если оплату когда-нибудь
включат, записи с платежами станет нельзя удалять.

## Общие причины: что можно закрыть одним движением

Эти находки не независимы. Четыре группы порождают сразу несколько пунктов выше.

| Причина | Что из неё следует | Что даёт |
|---|---|---|
| **Нет почтового провайдера** | 2.3 (сброс пароля), частично заявленное ограничение «уведомления только в кабинете» | Подключить один отправитель — и появляется сброс пароля плюс канал уведомлений. Явно не подменять заглушкой: клиенту покажут «отправили письмо», которого не будет |
| **Внешний вход создаёт аккаунт без профиля клиента** | 2.1 (нельзя записаться) | Собрать профиль клиента при первом входе: спросить телефон или сделать `clients.phone` необязательным и добрать его при записи |
| **Нет эндпоинта списка клиентов + слоты отдаются только свободные** | 2.5 (нельзя записать поверх занятого) | Оба эндпоинта правятся вместе: один отдаёт клиентов, второй должен уметь отдавать и занятое время по запросу |
| **Проверки идут по рабочей базе без уборки** | 2.7 (мусор в базе) | Прогонять проверки на копии базы либо заводить скрипт уборки по префиксу логина |

Пункт 1.3 из первой группы тоже одиноко не стоит: он лечится в одном месте —
перевести `bookings.starts_at`/`ends_at` в один тип записи и перестать полагаться на
строковое сравнение.

## Чего проверка не покрывала

- Инъекции в параметры SQL.
- Исчерпание лимитов запросов (проверялись только ограничения регистрации и входа).
- Массовое присваивание полей на остальных эндпоинтах, кроме роли при регистрации.
- Нагрузочное поведение при большом числе одновременных записей.
